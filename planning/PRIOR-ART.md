# placemat: prior-art survey

Surveyed 2026-10-05 by web search and by reading primary sources where they could be fetched. The two papers placemat leans on most (Kalibera & Jones 2013; Curtsinger & Berger 2013) were read in full. Statements about other tools come from their documentation, changelogs, pull requests or issues, linked inline. Anything not checked against a primary source is marked *(not verified)*. This survey is not exhaustive. Where it says "found no prior work", read that as "this survey found none".

placemat in one paragraph (details in [ISSUES.md](ISSUES.md), P001-P004). placemat tells whether a timing difference between two builds comes from the change or from code and data placement. It builds K code-layout builds (pads) of each version, each timed at one to three data settings, using designed code pads (low-discrepancy over the 4 KB period and the 64-byte phase) and designed data colours and steps (an allocator hook or interposer that offsets large allocations: colours by one constant offset up to a page or more, steps per block within the L1 set stride). It alternates the builds in paired rounds and stops adaptively once the interval is narrow enough. It reports t intervals over pads and uses permutation tests to attribute spread to code, data or run (ASLR), with Benjamini-Hochberg across cases. A companion half pins hot code with an order file, `-falign-functions=16`, and pads from an exact search so that no hot loop or hot entry span crosses a 4 KB boundary. A colouring allocator removed structural L1 set conflicts from a buddy allocator.

## Key findings

1. **The problem and the randomise-and-average remedy are well established.** Mytkowicz et al. (2009) named it *measurement bias* and proposed *setup randomisation*. Stabilizer (2013) re-randomises code, stack and heap at run time. Kalibera & Jones (2013) folded layout into a multi-level experimental design. lld has `--shuffle-sections` (2020) and `--randomize-section-padding` (2024, explicitly "to control measurement bias in A/B experiments"). hyperfine (2020) and BenchmarkDotNet (2021) perturb environment size and memory placement. placemat must not claim to be first at any of these.
2. **Kalibera & Jones (ISMM 2013) is the statistical ancestor.** Their levels (iteration < execution < compilation) and their interval at the highest level (a t interval over highest-level means) are what placemat does, with the pad (one code-layout build) as the compilation level. They also give a formula for choosing repetition counts at the lower levels, which placemat lacks and should borrow. They found that a randomised layout can shift performance *consistently* (mcf −6.8%), not just add noise.
3. **Stabilizer explicitly cannot do what placemat's data axis does.** Its paper says it "cannot break apart large heap allocations, and cannot add randomization to custom allocators" (§4). Its heap randomisation is a shuffle over small allocations. It targets x86, x86_64 and PowerPC; this survey found no arm64 support. It is not dead: one fork is tested with LLVM 21 and another with LLVM 12 (with crashes in its code and stack modes).
4. **Designed rather than random perturbations, attribution to code versus data versus run, and pinning plus verification together appear new.** Each has neighbours: .NET 6 adaptive loop alignment and Go's `func_align_32` pin alignment for stability, and BenchmarkDotNet shows multimodality. But this survey found no tool that measures sensitivity, attributes it, pins the hot code, and then shows the code-layout spread collapsed.
5. **Allocator colouring is old.** Bonwick's slab colouring (1994), Kessler & Hill's page colouring (1992), Rivera & Tseng's padding (1998), Afek, Dice & Morrison's cache-index-aware malloc (2011) and jemalloc's `cache_oblivious` (2015, a random cache-line offset within the first page of large allocations) all predate it. What is placemat's own is using colouring as a *designed experimental factor* through a hook in a custom allocator.
6. **Name.** No benchmarking or profiling project called placemat was found. The active collision is `cybozu-go/placemat`, a data-centre virtualisation tool for QEMU/KVM (Apache-2.0, about 94 stars, binary `placemat2`). The npm and RubyGems packages called `placemat` are dormant and unrelated. crates.io and PyPI have no `placemat`. The name is usable; check the GitHub org name before creating it.

## 1. Layout randomisation for sound performance evaluation

### 1.1 Mytkowicz, Diwan, Hauswirth, Sweeney: "Producing Wrong Data Without Doing Anything Obviously Wrong!" (ASPLOS 2009)
- **What.** Shows that UNIX environment size (which moves the stack) and link order (which moves code and data) change SPEC CPU results enough to reverse conclusions: about 33% typically and up to about 300% from an unused environment variable. Proposes *causal analysis* to detect bias and *setup randomisation* to avoid it. Their example: O3 speed-up for perlbench of 1.007 ± 0.003 under setup randomisation. [ACM](https://dl.acm.org/doi/10.1145/1508244.1508275), [PDF](https://users.cs.northwestern.edu/~robby/courses/322-2013-spring/mytkowicz-wrong-data.pdf).
- **Relation.** *Overlap:* placemat's whole premise. *Difference:* their perturbations are random link orders and environment sizes; placemat's are designed pads and colours, and it attributes the spread. *Borrow:* the terms *measurement bias* and *setup randomisation*. Their causal analysis (intervene on a suspected factor and see whether the effect follows) is what placemat's "culprits" analysis does for hot loops. *Avoid claiming:* that layout sensitivity is a new finding, or that perturbing environment size is new.

### 1.2 Curtsinger & Berger: STABILIZER (ASPLOS 2013), and its forks
- **What.** An LLVM pass plus runtime that randomises code at function granularity (functions are relocated on first call and re-randomised every 500 ms by default), the stack (a random pad of up to 4096 bytes per frame, from per-function pad tables) and the heap (a shuffle layer of N = 256 over a power-of-two size-class allocator). Re-randomisation makes run times approximately Gaussian (by the Central Limit Theorem over many layouts per run), so t-tests and ANOVA apply. Median overhead is 6.7%, and below 40% on all benchmarks. Headline result: LLVM `-O3` over `-O2` is indistinguishable from noise on SPEC CPU2006. [Paper PDF](https://people.cs.umass.edu/~emery/pubs/stabilizer-asplos13.pdf), [original repo](https://github.com/ccurtsinger/stabilizer) (LLVM 3.1; "bit rot means it no longer works with new versions of LLVM", per [plasma-umass/memory-landscape](https://github.com/plasma-umass/memory-landscape)).
- **Forks.**
  - [matthiasgoergens/stabilizer](https://github.com/matthiasgoergens/stabilizer): "tested with LLVM 21", clang and Flang front ends; the README still lists x86, x86_64 and PowerPC.
  - [magras/stabilizer-fork](https://github.com/magras/stabilizer-fork): LLVM 12, maintained by Hans Kristian Rosbach. Heap and link randomisation work; code and stack modes "seem to [have] some crashes".
  - [dendibakh/stabilizer](https://github.com/dendibakh/stabilizer): LLVM 9; "works on HelloWorld … more complex examples crash".
  - No upstream LLVM support exists.
- **Statements in the paper that matter to placemat.** "STABILIZER cannot break apart large heap allocations, and cannot add randomization to custom allocators. Programs that use custom allocators or operate mainly on small objects from a single large array may not have normally distributed execution times" (§4). On x86_64 it needs `MAP_32BIT`, "on some systems (Mac OS X), this flag is unavailable" (§3.5). Four benchmarks ran *faster* under code randomisation, which the authors attribute to the default layout being "slightly worse than the median layout" (§5.2).
- **Relation.**
  - *Overlap:* the same goal (separate a change's effect from layout effects) and the same three axes (code, stack, heap).
  - *Difference:* Stabilizer treats layout as a nuisance to average away inside each run. placemat treats layout as a factor to measure, attribute and then remove by pinning. Stabilizer randomises at run time and changes the binary measured (with overhead). placemat builds static variants of an otherwise unmodified build: code pads are an unused function, and the data hook is compiled into variant builds only. placemat targets large buffers in custom allocators, which is exactly Stabilizer's stated gap, and runs on arm64/Mach-O.
  - *Borrow:* the argument that many layouts per estimate make the estimate approximately normal (placemat's t interval over pads rests on the same idea, at the pad level); its heap shuffle as an optional small-object axis; its observation that the stock layout can sit in the tail.
  - *Avoid claiming:* "first tool to randomise code, stack and heap for benchmarking"; "Stabilizer no longer works" (maintained forks exist).

### 1.3 Other measurement-bias infrastructure and studies
- **Kalibera, Bulej & Tůma, "Benchmark Precision and Random Initial State" (SPECTS 2005)** and **Kalibera & Tůma, "Precise Regression Benchmarking with Random Effects" (EPEW 2006)**. Random effects at the level of process start and compilation, applied to Mono regression benchmarking: the forerunners of Kalibera & Jones (§6.1). [Kent record](https://www.cs.kent.ac.uk/pubs/2005/3143/index.html), [Springer](https://link.springer.com/chapter/10.1007/11777830_5). *Credit* as the origin of treating build-level randomness as a random effect.
- **Hocko & Kalibera, "Reducing performance non-determinism via cache-aware page allocation strategies" (WOSP/SIPEW 2010).** Physical page placement in the OS causes run-to-run variation; page colouring and bin hopping in the kernel reduce it. [ACM](https://dl.acm.org/doi/10.1145/1712605.1712640) (abstract only; *not verified* beyond the abstract-level description). *Relation:* the likely explanation class for placemat's unexplained "run lottery" (P002: the run-to-run spread not accounted for by the ASLR base; perhaps a physically indexed L2). *Borrow:* cite it when describing the run level.
- **de Oliveira, Petkovich, Reidemeister, Fischmeister: DataMill (ICPE 2013; SP&E 2016)**, a distributed benchmarking infrastructure that "automates the variation of hidden factors" (link order, environment size and others) across heterogeneous machines. [Project page](https://uwaterloo.ca/embedded-software-group/datamill), [SP&E](https://dl.acm.org/doi/abs/10.1002/spe.2382). Also **de Oliveira et al., "Why You Should Care About Quantile Regression" (ASPLOS 2013)**: [PDF](https://research.google.com/pubs/archive/41873.pdf). *Overlap:* systematic variation of layout factors. *Difference:* a hosted testbed, not a local tool, and no pinning or attribution per case. *Avoid claiming* that "automatically varying hidden factors" is new.
- **Barrett, Bolz-Tereick, Killick, Mount, Tratt, "Virtual Machine Warmup Blows Hot and Cold" (OOPSLA 2017)**, and its runner **Krun**, which fixes ulimits and controls the environment. [Paper](https://soft-dev.org/pubs/html/barrett_bolz-tereick_killick_mount_tratt__virtual_machine_warmup_blows_hot_and_cold_v6/). *Relation:* the steady state is not guaranteed; changepoint analysis. *Borrow:* when placemat sees two-speed switching, changepoint segmentation of the rounds is a principled alternative to the p90/p10 heuristic.
- **Antoch, Binder, Bulej, Farquet, Horký, Prokopec, Rosà, Tůma, "Experimental Evaluation Methodology for the Era of No Steady Performance" (PACMPL OOPSLA1, April 2026).** Intervals for workloads with steady segments separated by sudden changes. [PDF](https://d3s.mff.cuni.cz/files/publications/antoch_experimental_2026.pdf), [DOI](https://doi.org/10.1145/3839448). *Relation:* the formal treatment of the "two speeds run to run" behaviour placemat flags. *Borrow:* worth reading before finalising placemat's run-level model.

### 1.4 Code alignment effects (2015-2026)
- **Zia Ansari (Intel), "Causes of Performance Instability due to Code Placement in X86", LLVM Developers' Meeting, Nov 2016.** Random NOPs give ±20% swings; DSB (decoded-uop cache) and fetch-window mechanisms. [Slides](https://llvm.org/devmtg/2016-11/Slides/Ansari-Code-Alignment.pdf), [video](https://www.youtube.com/watch?v=IX16gcX4vDQ). Cited by pyperf's docs.
- **Victor Stinner, "My journey to stable benchmark, part 2 (deadcode)", May 2016.** Adding unused functions moved a CPython benchmark from 1201 ms to 1273 ms (two functions) or 1170 ms (one empty function); building with PGO removed the effect. [Blog](https://vstinner.github.io/journey-to-stable-benchmark-deadcode.html). *Closest practitioner precedent for "pin the layout to stabilise timings"*, by a different mechanism (PGO's hot/cold layout).
- **Denis Bakhvalov, "Code alignment issues" and "Code alignment options in llvm", Jan 2018.** Removing an unrelated function cost 10%; `-mllvm -align-all-nofallthru-blocks` and related flags. [Post 1](https://easyperf.net/blog/2018/01/18/Code_alignment_issues), [post 2](https://easyperf.net/blog/2018/01/25/Code_alignment_options_in_llvm).
- **Intel JCC erratum (Nov 2019).** Microcode stops jumps that cross or end on a 32-byte boundary from being cached in the DSB, at a cost of 0-4%. Mitigation: `-mbranches-within-32B-boundaries` (GNU as, LLVM 10). [Intel guidance](https://www.intel.com/content/www/us/en/developer/articles/technical/software-security-guidance/best-practices/mitigation-strategies-jcc-microcode.html), [Phoronix on LLVM 10](https://www.phoronix.com/news/LLVM-10-JCC-Option). *Relation:* the x86 analogue of placemat's "no hot loop across a boundary" rule, at 32 B rather than 4 KB. The Linux/x86 pad rule (P006) should consider it.
- **Abseil Performance Tip of the Week #39, "Beware microbenchmarks bearing gifts" (Kennelly & Evlogimenos, Jan 2021, updated Sep 2025).** 20% memcpy swings from layout; snappy's "load-bearing nops"; recommends Stabilizer-style perturbation. [Tip](https://abseil.io/fast/39).
- **.NET 6 adaptive loop alignment (Kunal Pathak, Mar 2021).** The JIT pads hot loops to 32 B (falling back to 16 B), with a padding budget that shrinks as the loop grows. It was motivated in part by benchmark instability: "even a tiny change unrelated to the method body … can … misalign the loop". [Blog](https://devblogs.microsoft.com/dotnet/loop-alignment-in-net-6/). *Closest precedent for placemat's padding rule:* a padding budget against a boundary rule, aimed at stability.
- **Go proposal #72130, `GOARM64=…,func_align_32` (Mar 2025, accepted).** Motivated partly by noise: 32-byte function alignment removed "spurious 60%" swings in a benchmark suite on Kunpeng 920, revealing a real 7% effect. [Issue](https://github.com/golang/go/issues/72130).
- **Wilde, Briongos, Soriente, Karame, "On Abnormal Execution Timing of Conditional Jump Instructions" (arXiv, Jan 2026).** Jump timing depends on uop-cache placement and the L1I offset (Skylake through Coffee Lake); 32-byte alignment removes the variation. [arXiv:2601.11696](https://arxiv.org/abs/2601.11696).
- **Practitioner precedent, 2026: namecheap/fast_mail_parser issue #240 (Aug 2026).** "Salted layout A/B": 4-8 builds whose layout is perturbed via rustc's `-C metadata=` salt, timed interleaved, with per-benchmark spread classified against a control floor and a 3% threshold. Reports 0-96% swings with byte-identical instruction streams on Zen. [Issue](https://github.com/namecheap/fast_mail_parser/issues/240). *Relation:* a project-local version of placemat's code-axis stage, which shows demand. *Avoid claiming* that nobody else runs layout-variant A/B in CI.
- **Apple Silicon.** This survey found no public documentation of a 4 KB code-boundary penalty on M1/M2 ([ocxtal's M1 notes](https://github.com/ocxtal/insn_bench_aarch64/blob/master/optimization_notes_apple_m1.md) cover the L1I and BTB, not this). macOS on Apple Silicon uses 16 KB pages, so placemat's 4 KB effect is **not a page crossing**. *Avoid claiming* a mechanism; state it as an empirical finding on M2 and keep the boundary configurable.

### 1.5 Data alignment and set conflicts
- **4K aliasing (Intel optimisation manual, "4K Aliasing").** A *store-to-load* false dependence when addresses differ by a multiple of 4096 (12-bit comparison in the memory-order buffer); about 5 cycles. [Explainer](https://richardstartin.github.io/posts/4k-aliasing). This is **not** the L1 set-conflict effect placemat found on M2 (buffers 0 mod 16 KB competing for the same L1D sets). Use distinct terms (see the terminology section).
- **Linux THP alignment regression (2024).** Commit efa7df3e3bb5, "mm: align larger anonymous mappings on THP boundaries", made large mmaps PMD-aligned. SPEC cactuBSSN regressed up to 600% "due to … TLB or cache aliasing due to the aligned boundaries"; the fix in 6.12 limits alignment to PMD-multiple sizes. [Patch thread](https://www.spinics.net/lists/stable/msg787692.html), [Phoronix](https://www.phoronix.com/news/Intel-Linux-3888.9-Performance). *Relation:* the same structural mechanism as placemat's buddy-allocator finding (allocations aligned to their own size alias), found in the kernel. A good citation for "alignment by construction causes set conflicts".
- **BenchmarkDotNet issue #1513 (Adam Sitnik, Aug 2020).** Microbenchmarks flip between modes for days at a time ("_____~~~~~~_____"), traced to the alignment of arrays allocated once in setup. [Issue](https://github.com/dotnet/BenchmarkDotNet/issues/1513). This led to MemoryRandomization (§3).

## 3. Benchmark frameworks and their stance on layout

## 4. Layout optimisers that also pin

- **Pettis & Hansen, "Profile Guided Code Positioning" (PLDI 1990).** The original function and block ordering. *Credit* as the root.
- **Ottoni & Maher, "Optimizing Function Placement for Large-Scale Data-Center Applications" (CGO 2017): hfsort / C3.** [Semantic Scholar](https://www.semanticscholar.org/paper/Optimizing-function-placement-for-large-scale-Ottoni-Maher/0ae970cfd313d91a5341a3deb2c3a25e863182c8). placemat's `order.py` is "C3-style" (each function merged behind its heaviest caller, with cluster caps and a density sort). *Credit explicitly.*
- **BOLT (Panchenko et al., CGO 2019; Lightning BOLT, CC 2021).** A post-link binary optimiser: block reordering, function splitting, hfsort. [PDF](https://jnamaral.github.io/CDOL/papers/PanchenkoCGO19.pdf). ELF only (also Mach-O work in progress upstream *(not verified)*).
- **Propeller (Shen et al., ASPLOS 2023).** Profile-guided relinking with basic-block sections; 1.1-8% over PGO and ThinLTO. [ACM](https://dl.acm.org/doi/10.1145/3575693.3575727).
- **Balanced partitioning for mobile function layout (Meta, LCTES 2023)**, now in lld as `--bp-*`. [arXiv](https://arxiv.org/pdf/2211.09285).
- **Order files in production.** [Chromium's orderfile pipeline](https://chromium.googlesource.com/chromium/src/+/main/docs/orderfile.md) (instrumented builds on device; 4-7% gains; Speedometer 3 added to the profile set); [Android NDK order files](https://developer.android.com/ndk/guides/orderfile) ([blog, Nov 2023](https://android-developers.googleblog.com/2023/11/orderfiles-in-android.html)); Apple's `-order_file` (Xcode's "Order File" build setting).
- **Pinning for *stability* rather than speed.** Precedents found: Stinner's PGO (2016), .NET 6 loop alignment (2021), Go `func_align_32` (2025), snappy's load-bearing nops (Abseil #39). **This survey found no prior work that uses a linker order file, with or without pads, specifically to reduce benchmark noise, or that verifies the result by measuring code-layout spread before and after.** All the order-file work above targets start-up, i-cache/iTLB or page-fault locality.
- **Relation.** *Overlap:* placemat's pinning reuses standard machinery (profile → C3 clusters → order file). *Difference:* the objective is invariance. Hot functions should not move when unrelated code changes, and the pinned layout should avoid known-bad boundaries. placemat's exact pad search ("no hot loop and no hot entry span crosses 4 KB, fewest pad bytes") is closer in spirit to .NET's padding budget and the JCC-erratum rules than to BOLT or Propeller. *Borrow:* on ELF, use lld's `--symbol-ordering-file` with `--shuffle-sections` for the unpinned rest, and consider BOLT or Propeller as the pinning back end where available. *Avoid claiming* that a pinned layout is optimal or layout-independent: placemat's own data (P003) and Kalibera & Jones §8.2 show that any fixed layout has its own "luck".

## 5. Allocator colouring and heap perturbation

- **Kessler & Hill, "Page Placement Algorithms for Large Real-Indexed Caches" (ACM TOCS, Nov 1992).** Page colouring and bin hopping in the OS. [ACM](https://dl.acm.org/doi/10.1145/138873.138876) *(link inferred from the citation; not opened)*. *Credit* as the origin of "colouring".
- **Bonwick, "The Slab Allocator: An Object-Caching Kernel Memory Allocator" (USENIX Summer 1994).** **Slab colouring:** each slab's first object is offset by a rotating colour taken from the slab's unused space, so objects in different slabs map to different cache lines. [PDF](https://people.eecs.berkeley.edu/~kubitron/courses/cs194-24-S14/hand-outs/bonwick_slab.pdf). *This is the direct ancestor of placemat's colouring allocator:* the colour comes from spare room, rotates by a counter, and costs no extra memory. *Credit explicitly.*
- **Rivera & Tseng, "Data Transformations for Eliminating Conflict Misses" (PLDI 1998).** Compiler inter-variable padding (base addresses) and intra-variable padding (array dimensions); 6% average time reduction. [ACM](https://dl.acm.org/doi/abs/10.1145/277650.277661).
- **Afek, Dice & Morrison, "Cache Index-Aware Memory Allocation" (ISMM 2011).** malloc made "index-aware", spreading blocks over L1 indices to cut index conflicts caused by imbalanced block placement. [dblp](https://dblp.org/db/conf/iwmm/ismm2011.html), [academia.edu](https://www.academia.edu/792352/Cache_index_aware_memory_allocation). *The closest academic prior art to placemat's allocator change.* *Credit explicitly.*
- **jemalloc `opt.cache_oblivious` (jemalloc 4.0.0, Aug 2015).** For large allocations without alignment constraints, a pseudo-random multiple-of-cache-line offset within the first page (64 positions with 4 KiB pages and 64 B lines), at the cost of one extra page; "if this feature is disabled, all large allocations are page-aligned as an implementation artifact, which can severely harm CPU cache utilization" ([man page](https://man.archlinux.org/man/jemalloc.3.en), [4.0.0 announcement](http://jemalloc.net/mailman/jemalloc-announce/2015-August/000018.html)). *Difference:* random, within one 4 KiB page; placemat's measurement colours and steps are deterministic and reproducible (colours up to a page or more; steps within the 16 KB L1 set stride, derived from block position, hashed per variant); Amber's own colouring fix used a deterministic counter. Note that 64 offsets × 64 B cover only 4 KiB, so on an M2-class L1 (16 KB stride) jemalloc's colouring would cover a quarter of the stride *(an inference, not measured)*.
- **TCMalloc.** Large objects are page-aligned ([design doc](https://google.github.io/tcmalloc/design.html)); no colour offset found. **mimalloc.** Its technical report and README describe randomised free lists and address-randomised OS-level blocks, aimed at security ([TR](https://www.microsoft.com/en-us/research/uploads/prod/2019/06/mimalloc-tr-v1.pdf)); no deliberate cache colouring of large blocks found. **glibc.** Large blocks come from mmap with a small header, so payloads sit at a fixed offset mod 4 KiB *(from general knowledge; not re-checked here)*. All three are candidates for placemat's interposer (P004) to perturb.
- **DieHard (Berger & Zorn, PLDI 2006) and DieHarder (Novark & Berger, CCS 2010).** Randomised placement over an over-provisioned heap, for memory safety and security; Stabilizer can use DieHard as its substrate. [memory-landscape](https://github.com/plasma-umass/memory-landscape). *Relation:* heap randomisation as an engineering primitive. Not designed for measurement and costly.
- **Stabilizer's heap shuffle and BenchmarkDotNet's MemoryRandomization:** see §1.2 and §3. Both are random and both act on small objects or the GC heap; neither colours large buffers in a custom allocator.
- **Savage & Jones, "HALO: Post-Link Heap-Layout Optimisation" (CGO 2020).** Profile-guided grouping of heap objects by allocation context. [ACM](https://dl.acm.org/doi/10.1145/3368826.3377914). The data-side counterpart of order files. A possible future "pin the heap" direction; not needed for colouring.
- **Relation overall.** *Overlap:* colouring large blocks to avoid set conflicts is established (Bonwick, Afek et al., jemalloc). *Difference:* placemat uses the colour as a **designed experimental factor** (an environment-controlled hook that is compiled into variant builds only), alongside a production colouring policy. Its finding concerns a *buddy* allocator, where alignment by construction makes every large payload land at the same offset mod the set stride, so a dummy allocation cannot move it. The Linux THP regression (§1.5) is the same mechanism in the kernel. *Avoid claiming* that colouring, or the counter-based colour choice, is new; claim the measurement use and the hook protocol.

## 6. Statistical methodology

### 6.1 Kalibera & Jones, "Rigorous Benchmarking in Reasonable Time" (ISMM 2013), read in full
[ACM DOI 10.1145/2464157.2464160](https://doi.org/10.1145/2464157.2464160), [Kent repository PDF](https://kar.kent.ac.uk/33611/). Full derivations are in the technical report *Quantifying Performance Changes with Effect Size Confidence Intervals* (Kent TR 4-12, 2012; [arXiv:2007.10899](https://arxiv.org/abs/2007.10899), posted 2020).

What they do:
- **Variables (§3).** *Controlled* variables (chosen settings), *random* variables (non-deterministic, sampled by repetition) and *uncontrolled* variables (fixed but unknown, which cause bias). "The experimenter's first task is to identify uncontrolled variables … and modify the experimental system so that these become either controlled or random. For example, randomising link order turns an uncontrolled variable into a random one."
- **Levels (§3).** "Points of potential repetition" in the sequence compilation → execution → iteration. The *highest* level is the first source of variation (compilation); the *lowest* is the measured operation (an iteration). "At the very least, repetition must be done at the highest level that has random variation to avoid bias."
- **Layout as the compilation level (§8).** They patched gcc to randomise function order within modules, module order and global order under LTO, then rebuilt each SPEC CPU binary 30 times. On their x86 platforms the layout variation at reference sizes was small (below 1% for most benchmarks), *but* "randomised layout can impact performance *consistently*, and not just introduce noise" (xalancbmk 3.3% and mcf 6.8% slower under randomisation). On DaCapo/HotSpot they found little build-level variation.
- **Dimensioning (§9).** Run an initial experiment with r_i repetitions at each level and estimate variance components T_i² with unbiased estimators (equations 1-2). With per-level costs c_i, the optimal repetition count at each level *below the top* is r_i = ⌈√(c_{i+1}·T_i² / (c_i·T_{i+1}²))⌉ (equation 3). The top-level count is set by the precision wanted.
- **Interval (§9.3, §10).** A t interval at the highest level: means over everything below each top-level repetition, ν = r_n − 1 (equation 4). The ratio of two systems' means uses **Fieller's** interval (equation 5); its half-width is roughly √(e² + e′²), where e and e′ are the two relative half-widths (equation 6). Their recommendation: report effect-size confidence intervals, not significance tests.
- **Independence (§6).** Lag plots and ACF to find the iteration at which a benchmark reaches an independent state; do this manually, once per benchmark, VM and platform.

How placemat relates:
- *Overlap (credit this):* placemat's interval is equation (4) applied at the **pad** (build) level (a t interval over per-pad summaries), with the pad playing the role of K&J's compilation level. Their "turn an uncontrolled variable into a random one" is exactly the code and data perturbation. Their "or a controlled one" is exactly pinning (an order file and pads turn code placement into a controlled variable).
- *Differences:*
  - placemat's variants are **designed** (a joint Kronecker (low-discrepancy) sequence over pad and colour, with reproducible pseudo-random hashed steps), not random rebuilds.
  - It is a **paired** design (both versions timed in the same round, so per-round ratios block out drift) rather than two independent systems with Fieller's ratio interval.
  - It varies code at the top level (pads) and data within each pad (colour and step settings), plus a run covariate, and **tests** each with permutation tests; K&J estimate variance components but attribute nothing to causes.
  - It stops **adaptively** on interval width rather than dimensioning up front.
- *Borrow:*
  1. The dimensioning formula: choose rounds per pad versus the number of pads from measured variance components and costs (a pad's build is about 8 s; a round costs a case's run time). This is a principled replacement for placemat's fixed rounds and directly serves P005 ("make the stage faster").
  2. K&J's level names in the reports.
  3. The Fieller interval as a check when the pairing is weak.
  4. Their warning that a randomised layout can shift the mean as well as widen the interval: report the stock-layout result next to the layout-averaged one, as placemat already does.
- *Avoid claiming:* that multi-level repetition, repetition at the build level, or treating layout as a random effect is new. All three are in K&J (and in Kalibera, Bulej & Tůma 2005 and Kalibera & Tůma 2006).

### 6.2 Georges, Buytaert & Eeckhout, "Statistically Rigorous Java Performance Evaluation" (OOPSLA 2007)
Confidence intervals over multiple VM invocations, with iterations within each, and a steady-state window chosen by coefficient of variation; ANOVA for multiple alternatives. OOPSLA Most Influential Paper award in 2017. [ACM](https://dl.acm.org/doi/10.1145/1297027.1297033), [PDF](https://dri.es/files/oopsla07-georges.pdf). *Relation:* a two-level (invocation, iteration) predecessor of K&J. K&J show that its automatic warm-up heuristic misfires. *Credit* as general background.

### 6.3 Cloud and CI benchmarking
- **Abedi & Brecht, "Conducting Repeatable Experiments in Highly Variable Cloud Computing Environments" (ICPE 2017): RMIT (randomised multiple interleaved trials).** [PDF](https://cs.uwaterloo.ca/~brecht/papers/icpe-rmit-2017.pdf). *Credit* for placemat's alternation of builds in rounds. placemat does randomise the order within a round (RMIT-style): DESIGN §5.1.
- **Laaber, Scheuner & Leitner, "Software Microbenchmarking in the Cloud. How Bad is it Really?" (EMSE 2019).** [PDF](https://www.ifi.uzh.ch/dam/jcr:326f9543-d719-4e8c-a27e-d5a5cace1abf/emse_smb_cloud.pdf).
- **Laaber, Würsten, Gall & Leitner, "Dynamically Reconfiguring Software Microbenchmarks" (ESEC/FSE 2020).** Stops JMH forks early using the coefficient of variation, relative CI width or Kullback-Leibler divergence; saves 48-86% of time while keeping results for about 79-88% of benchmarks. [PDF](https://www.ifi.uzh.ch/dam/jcr:2e51ad81-856f-4629-a6e2-67d382d337c2/fse20_author-version.pdf). *Relation:* adaptive stopping on CI width in a benchmark harness; placemat's stopping rule has this precedent. *Avoid claiming* adaptive stopping is new.

Not suitable for placemat's cache-sensitive cases, since the two programs would share L2 and bandwidth (P005 already rules out parallel timing).

Evaluates 29 system configurations (turbo, C-states, SMT, pinning, governors, heap) for short benchmarks. Layout is not a studied factor, as far as the artifact shows.
- **Japke, Koch, Lukasczyk, Bermbach, "Towards an Optimized Benchmarking Platform for CI/CD Pipelines" (arXiv, Oct 2025).** [arXiv:2510.18640](https://arxiv.org/abs/2510.18640). Composable benchmark-suite reductions. Relevant to P005, not to layout.

### 6.4 Estimators, steady state and sequential stopping
- **Chen & Revels, "Robust benchmarking in noisy environments" (HPEC 2016; arXiv:1608.04295).** BenchmarkTools.jl tunes evaluations per sample and argues for the minimum. [arXiv](https://arxiv.org/pdf/1608.04295). **Tratt, "Minimum Times Tend to Mislead When Benchmarking" (blog, Aug 2019)** argues the opposite. [Post](https://tratt.net/laurie/blog/2019/minimum_times_tend_to_mislead_when_benchmarking.html). *Relation:* placemat's per-variant medians and trimmed means sit between the two. Under layout perturbation the minimum would pick the luckiest layout, which defeats the purpose. Say so in the docs.
- **Mittal, Bruel, Milojicic, Frachtenberg, "Adaptive Stopping Rule for Performance Measurements" (PMBS workshop at SC 2023).** [ACM](https://doi.org/10.1145/3624062.3624202) (paywalled; content *not verified*).
- **Fixed-width sequential intervals.** Chow & Robbins (Annals of Mathematical Statistics, 1965) is the classical result. Singham & Schruben, "Finite-Sample Performance of Absolute Precision Stopping Rules" (INFORMS J. Computing, 2012; [link](https://pubsonline.informs.org/doi/10.1287/ijoc.1110.0471)) shows coverage can fall short of nominal for small samples. *Relation:* stopping on width (never on significance), as placemat does, is the standard approach, but coverage is only approximately nominal. *Avoid claiming* exact 95% coverage under adaptive stopping. placemat's null validation (about 6.7% of intervals missing 1, i.e. no change) is consistent with this, and should be stated that way.
- **Melis, "The Right Call for Software Benchmarking: Consistent Decisions in Stateful Environments" (arXiv, Jun 2026).** Frames benchmarking as a decision problem with designs that admit consistent estimators of contrasts. [arXiv:2606.17261](https://arxiv.org/abs/2606.17261). Worth reading for the paired-contrast framing.
- **Hoefler & Belli, "Scientific Benchmarking of Parallel Computing Systems: Twelve ways to tell the masses when reporting performance results" (SC 2015).** General reporting rules (CIs, non-parametric statistics, no summarising by the arithmetic mean of ratios) *(from knowledge)*.
- **Multiple testing.** Benjamini & Hochberg (JRSS B, 1995). No benchmark tool surveyed applies an FDR correction across cases; benchstat explicitly does not. Permutation tests are standard (Fisher, Pitman). Their validity in placemat rests on exchangeability of pad labels (and of a pad's two compared variants) within a batch's rounds, which should be stated.

## (a) What placemat would be the first or only tool to do

Stated with care: "as far as this survey found, no existing tool…". Each ingredient has precedent; the claims are about the combination and two specific gaps.

1. **Designed, joint code-and-data layout variants with per-case attribution.** Existing tools randomise (Stabilizer, lld `--shuffle-sections` / `--randomize-section-padding`, hyperfine, BenchmarkDotNet, DataMill) and then average or widen the distribution. None found builds a *designed* set of variants over both code position (a low-discrepancy sequence over the 4 KB period and 64-byte phase) and data placement (low-discrepancy colours; steps that are reproducible and pseudo-random per block pair), and then attributes each case's spread to code, data or run with permutation tests and FDR control across cases.
2. **Colouring large buffers in a custom allocator as an experimental factor.** Stabilizer explicitly cannot randomise custom allocators or large allocations. BenchmarkDotNet's approach relies on reallocating managed objects. placemat's hook protocol (`placemat_colour(k, size, spare_room)`, compiled into variant builds only) fills that stated gap.
3. **Measure, then pin, then verify.** No tool found pins hot code with an order file, function alignment and an exact pad search against a profile-weighted boundary rule (no hot loop and no hot entry span across the boundary), *and* uses the same harness to show that code-layout spread has collapsed while real changes still show. Pinning for stability has precedents (.NET loop alignment, Go `func_align_32`, Stinner's PGO), but none uses order files or verifies the result statistically.
4. **Apple Silicon / Mach-O support.** Stabilizer's documented targets are x86, x86_64 and PowerPC; lld's options are ELF only; ld64 has no shuffle or padding option. placemat's source-level pad function and ld64 order-file pinning work on macOS arm64. *Keep this claim modest:* it is a platform gap, not a method.

Not claimable: layout sensitivity itself; randomising layout for benchmarking; multi-level designs, or the build level as a random effect; paired or interleaved runs; adaptive stopping on CI width; allocator colouring; order files; and that pinning gives the "true" or layout-independent speed.

## (c) Recommended terminology

| placemat concept | Use | Notes |
|---|---|---|
| repetition inside one timed sample (`reps`) | **iteration** (K&J's lowest level) | The tool's "repetition series" is a series of iterations. |
| one process run of one build in a round | **execution** (K&J) | "Run" is fine informally; reports should say "execution level". |
| one paired pass over base and branch | **round**, described as a **block** in the design | Pairing within a round is *blocking*; per-round ratios are *paired contrasts*. |
| a padded build | **pad**, the **compilation (build) level** in K&J terms | A **layout variant** is one pad timed at one data setting; say "layout variant", not "variant". |
| spread across variants | **layout spread**, a **variance component** at the build (pad) level | Matches K&J's T_i². |
| perturbing code or data placement | **setup randomisation** (Mytkowicz) when random; **designed perturbation** for placemat's sequences | Avoid "randomised layouts" for placemat's own variants: they are not random. |
| systematic error from a single layout | **measurement bias** (Mytkowicz) | |
| pinning hot code | turning placement from an **uncontrolled variable** into a **controlled** one (K&J §3) | Perturbing turns it into a **random** one. Say both, in those words. |
| interval over pads | **effect-size confidence interval** (K&J) for the ratio | Say "t interval over pads (code-layout builds; K&J eq. 4 at the build level)". |
| colour offset in the allocator | **colouring** (Bonwick; page colouring, Kessler & Hill) | |
| buffers competing for the same L1 sets | **L1 set conflicts** (cache index conflicts, Afek et al.) | **Do not call this "4K aliasing"**, which names Intel's store-to-load false dependence. "Set aliasing" is acceptable if defined. |
| a hot loop or entry span across 4 KB | **4 KB boundary crossing** | **Not "page crossing"** on macOS arm64 (16 KB pages). Keep the boundary a parameter; the mechanism on M2 is unexplained. |
| "layout-sensitive" flag | **layout-sensitive case** | Define it as "spread over pads exceeds the threshold, with permutation p ≤ 0.01 that survives BH", per P002. |
