## Deviations and decisions made during extraction

- Arms given as the same git revision share one exported tree and one set of binaries (a stricter null than the prototype's two worktrees; DESIGN §5.7's "main against main is not a perfect null when base and branch run from different directories" no longer applies to git arms).
- Amber's hook recovers a block's offset from its address mod 16 KB (regions are 16 KB aligned on macOS arm64), so it refuses to colour on smaller pages and drops offsets of 16 KB or more: colour and step spans must be at most 16 KB for Amber.
- The hook header's `placemat_active()` is also true when only `PLACEMAT_LOG` is set, so at the stock setting blocks are counted and hashed (the run covariate is available at every setting).
- Protocol suites run a regression series only when they declare `series = true` (a harness that ignores PLACEMAT_SERIES would otherwise lose its cases); K `out[]` suites always can.
- bench.k/bench-std.k values stay in the units Amber prints (ms for bench-std), as the prototype compared them with the 5 ms threshold; so their threshold is the fast-case 10%, as before.

## Findings

- **The prototype's measurement hook changed Amber's growth points.** Its offset shrank `cap()`, so `aa()` growing a coloured vector re-allocated within the class at every step (DESIGN §7's growth rule, learnt on the colouring allocator, was never applied to the measurement hook). Checked on the equality scripts: with the rule missing, a hashed step made 11,545 large allocations against 2,825 at the stock setting (win_eq), and 30-65% of blocks were wrapped. With the rule (the hook now asks for the next class when an owned coloured vector would still fit uncoloured), every setting makes exactly the stock allocations (2,825 / 732 / 101 for win_eq / grp_eq / fnd_eq), every large block is offset, at most 6% wrapped, outputs identical at every setting. So the reference runs' data-axis variants carried extra copying; the re-validation should show smaller data effects where the copies mattered.
- **This machine is noisy under the other sessions' load.** The first regression run (d1, pinned against main) had a within-pad variance about 70x the reference's (S1 0.025-0.037 against 4e-4), rising through the run; a fixed 15 ms CPU loop varied by 10-20%. placemat now has a noise probe (lock.py; `[machine] max_noise`, `wait`): it waits, holding the lock, until the probe's spread is at most the limit, and records the probe per batch in the report. Amber's config uses 5%. d1 is to be re-run.
