Companion documents: [ISSUES.md](ISSUES.md) (work items P001-P014), [PRIOR-ART.md](PRIOR-ART.md) (what exists, what to credit, what not to claim), [amber-validation/](amber-validation/) (the runs on Amber that this design rests on). ## 1. What placemat is for

placemat answers one question about a change to a compiled program: **is this timing difference caused by the change, or by where the code and data happened to land?**

A change to one function moves every function linked after it. On Amber, moving code alone changed unrelated benchmarks by 10-35%, or doubled them. On Amber (Apple M2), one dict amend ran 2× slower in about one layout in 60; date grading ran 10% slower in a pinned build that left two of its loops across a 4 KB boundary, and at normal speed once they were moved off it; and window kernels ran 2-2.8× slow because every large buffer sat at the same offset mod 16 KB, and switched between two speeds from run to run with where the allocator's region landed under address randomisation, a repeatable function of its base (§5.4). A single timing of each build cannot tell these from real effects. This is *measurement bias* (Mytkowicz et al., 2009, who also moved results by several percent through the environment's size alone, which shifts where the stack starts).

placemat does three things:
1. **Measure:** time the base and each change across designed layout variants, so the result no longer depends on one layout, and attribute each case's spread to code placement, data placement (designed offsets, where the allocator's regions land, and what the process allocated before), stack placement, or run-to-run noise (history and stack: planned, §5.4, §5.5).
2. **Fix (optional):** turn placement from an uncontrolled variable into a controlled one (Kalibera & Jones's terms; Measure makes it a random one): pin hot code with an order file, function alignment and pads; colour large allocations so buffers used together stop sharing cache sets.
3. **Watch:** once fixed, check changes cheaply, and re-run the full measurement now and then to catch what the fixes no longer cover.

Non-goals: it is not a profiler, not a code optimiser (it does not try to find the *fastest* layout), and it does not claim a layout-independent "true speed". It reports effects with intervals over layouts, next to the result in the layout the user actually ships.

## 2. Vocabulary

The levels follow Kalibera & Jones (ISMM 2013) and *measurement bias* follows Mytkowicz et al. (2009); the rest are placemat's own terms (PRIOR-ART.md §(c)).

| term | meaning |
|---|---|
| **case** | one named benchmark measurement (e.g. `s_msum100` in Amber's `win.k` suite) |
| **iteration** | one repetition of the measured operation inside a timed sample (the lowest level) |
| **execution** | one process run of one build at one data setting, running one suite's cases (or one case, under case isolation: planned, §5.4) |
| **slot** | one thing timed in a round: a layout variant, the stock builds (first batch), the anchor (later batches), or another contrast-only slot (the isolation and stack slots, planned, §5.4, §5.5) |
| **round** | one pass over every layout variant of the current batch (plus the stock builds in the first batch, or the anchor in later ones, and any other contrast-only slots), for every arm, in random order, each variant's arms back to back: a *block* in the statistical sense (elsewhere a block is an allocated memory block) |
| **arm** | one version being compared: the base and one or more changes |
| **pad** | one code-layout build of an arm, made by linking a pad function of P bytes before the code under study ("pad j" is the j-th such build; pads are also named by their size): the *build level*, the highest level of repetition, and the unit of the interval |
| **pin pads** | pad functions placed between the ordered hot functions of a pinned build (§6.3); not the code-axis pad |
| **layout variant** | one (pad, data setting) combination: a pad's build timed at one data setting; each pad has three (no offset, its colour, its step), two when only one of colour and step is varied, or one when the data axis is skipped |
| **colour** | a constant offset added to every coloured allocation: moves the data relative to fixed things (page boundaries, uncoloured allocations, static data, the stack) |
| **step** | a per-block offset that differs from block to block, so coloured buffers move relative to *each other* (their L1 set conflicts): hashed by default (block k gets a pseudo-random offset from the variant's seed), or linear (block k moves by s·(k+1)); k comes from the block's position (§5.3) |
| **unit, span_s, span_c** | offsets are whole units (the cache line, 64 B by default; never finer than the project's alignment guarantee); a step is taken mod span_s (the L1 set stride), a colour mod span_c (§5.3) |
| **data setting** | a (colour, step) pair, where the step is *off* or a step value/seed; (0, off) means no offset (the stock placement only for a hooked build of an allocator that otherwise places blocks identically; see §5.3) |
| **stock** | an arm's build with no code-axis pad, hook, colouring allocator or interposer: the build as the project ships it (for a pinned arm, built with its order file and pin pads, §3.4) |
| **placemat run** | one invocation of `run`, `survey` or `check`, with its raw file; a process run of a build is an *execution* |
| **data method** | how offsets are applied: a **hook** (`placemat.h` compiled into the project's own allocator), the **colouring allocator** (below), the **interposer** (a preloaded replacement for malloc), or none (§7) |
| **code axis / data axis / run** | the designed sources of variation (where code sits; where large buffers sit relative to their placement) and what differs between executions (the region lottery, the stack's position, the machine; §5.4, §5.5) |
| **batch** | the pads timed together, in the same rounds: a first batch, then more pads a batch at a time while a case's interval is wide (§5.7) |
| **anchor** | pad 0 at the stock setting, timed again in each later batch to put its absolute times on the first batch's scale (§5.7) |
| **run covariate** | a per-execution measurement that may explain run-to-run spread, read from the data method's log: the ASLR region base (or, under a hook that reports no region, the first coloured block's address), or a hash of k values (§5.1); planned: one from the child's resource usage (§5.8), and the initial stack offset (§5.5) |
| **contrast-only slot** | a slot compared with stock-setting variants (the stock slot with all of them; the isolation and stack slots with their own pad's) but not itself a layout variant (not in the per-pad mean, the code test or batch counting): the stock slot today; the isolation and stack slots planned (§5.4, §5.5) |
| **region lottery** | where the allocator's regions land in each execution under address randomisation (§5.4) |
| **natural mix** | the proportions in which the region lottery's outcomes occur unaided on this machine; estimates standardised to it do not depend on how one run happened to draw (§5.7) |
| **heap history** | which block, and so which offset within its region, each buffer gets, set by what the process allocated and freed before the case (§5.4) |
| **case marks, fingerprint** | marks the harness writes into the data method's block log before each case (`placemat_mark`), and the per-case record of block addresses they allow (planned, §5.4) |
| **stack offset** | where the initial stack pointer sits, mod the L1 set stride; set by the bytes above the stack and its randomisation (planned, §5.5) |
| **thread count** | T, the number of threads a case runs with; part of the case's identity (planned, §5.8) |
| **layout spread** | how much a case's time varies across the layout variants of one arm, reported as the range of their medians (§5.7); its code part corresponds to Kalibera & Jones's build-level variance component |
| **layout-sensitive case** | a case whose spread over the code (or data) axis exceeds the threshold, with a permutation p ≤ 0.01 that also survives the false-discovery-rate correction across cases |
| **hot entry span** | from a hot function's entry to its last sampled offset under 1 KB that holds at least 10% of the function's samples |
| **hot loop** | a small loop (a backward branch within ≤256 B) in a hot-set function |
| **pinned** | built so the hot code's addresses do not depend on unrelated code |
| **stock setting** | the data setting (0, off); a *stock-setting variant* is a pad timed there. Not the stock build: under the colouring allocator or the interposer it is not even the stock placement (§7) |
| **coloured setting, stepped setting** | (c_j, off) and (0, step_j): a pad timed at its colour, or at its step |
| **coloured build** | a build of the project with its own colouring of large allocations (a real change, §3.2), as against placemat's measurement offsets |
| **colouring allocator** | placemat's `placemat_alloc.c`: a wrapper over malloc, installed through a project's allocator API, that over-allocates large blocks to offset them (§7); not Amber's own colouring fix |
| **4 KB boundary crossing** | a hot loop (or a hot function's hot entry span) straddling a 4 KB address boundary (not "page crossing": macOS arm64 pages are 16 KB, and the mechanism is unexplained) |
| **L1 set conflicts** | buffers used together mapping to the same L1 sets (not "4K aliasing", which is Intel's store-to-load false dependence) |

## 3. Lifecycle: initial setup, steady state, and periodic audits

The expensive measurement is not something a project should run on every change forever. It answers "do we have a problem?", then pays for the fixes, then mostly stands guard. placemat is organised around four modes; a project moves through them, and returns to the first two when something changes underneath it. The four modes map onto §1's three things: the survey is Measure, Fix is Fix, and the steady state and audits are Watch.

### 3.1 Survey: "do we have a problem?"

*When:* first use; after a compiler, linker, allocator or CPU change; when an audit (§3.4) finds something new.

*What:* the full design on the stock build. Main against itself (a null run: any "change" is a false positive, and the layout spread of every case is measured), and a handful of recent real changes. Both axes, all cases, a fixed and generous pad count (`placemat survey` uses 12 pads with the data axis on, 16 without, in one batch: adaptive stopping on the change interval would stop most cases of a null run at the first batch, where the code test has little power, as the Lua survey found; a fixed count fixes the early stop, but the code test's power under disturbed rounds is a separate problem, §11 item 10), and targeted variants for rare windows (§5.6).

*Output:* per case, its code spread, its colour and step contrasts, its run-covariate effect (and, from `placemat twospeed`, its run-to-run switching), and (planned) its isolation and stack contrasts (§5.4, §5.5), with the layout-sensitive cases listed and, for each, the "culprits" (the loops that cross a boundary only in the slow variants, from `placemat culprits` while the run's binaries exist; the buffers that conflict only at the slow data settings, from the fingerprint, §5.4: planned). From these, the user draws a verdict for the project (placemat does not compute one):
- **No meaningful spread:** the screening pass (§3.3; planned) is enough; stop here.
- **Code spread:** pinning (§3.2) will probably help.
- **Data spread:** colouring (§3.2) will probably help, and may be a real speed-up, not just a measurement fix (it was on Amber: window kernels 2-2.8× faster, a grouping case 2.5×).
- **Run spread** (switching between speeds from run to run): on Amber it was data placement under the region lottery (§5.4), and colouring removed it; on Lua it was machine noise (both arms slow in the same rounds), so compare the arms' slow rounds before blaming placement.

*Cost:* hours. The Amber prototype spent about 12-50 s per case with two variants per pad (measured on runs of up to 52 cases), so an estimated 40 min to 3 h per comparison of ~200 cases with the prototype's adaptive design (median 12 layout variants per case). A `placemat survey` times 12 pads × 3 data settings = 36 layout variants per case, about three times that median: by that ratio, roughly 2-9 h per comparison of ~200 cases (an extrapolation, not measured; P005). Run it rarely and keep its raw data.

### 3.2 Fix: pin and colour, then verify

*Pin* (§6.3): profile the benchmark set, choose the hot set (~95% of in-binary samples), write the order file, align functions, compute pads so no hot loop or hot entry span crosses a boundary, verify after linking. *Colour* (§7): build the project's allocator with colouring of large blocks (a real change to the project), or, for measurement only, use placemat's interposer, colouring allocator or hook.

*Verify:* re-run the survey's comparisons on the fixed builds. The code spread should collapse for the pinned cases while real changes still show (on Amber: 9-21 cases per run flagged by the prototype's uncorrected test → 0 in the order-file-only build and in the recommended pinned build (0-8 in other pinned variants, mostly chance flags and the data-placement windows); a false +13.5% → +0.9%, with the change's real costs, about +2-6%, intact). The data spread and the run switching should collapse once coloured. If they don't, the survey's culprits say where to look.

A project may stop after measuring, or take only one fix. Which fixes are in place decides what the steady state may skip; recording them in the configuration is planned (today the user chooses, e.g. `--data none` once colouring is built in).

### 3.3 Steady state: cheap checks on each change

*When:* every change worth timing (a pull request, a candidate fix).

*What:* placemat drops what the fixes have made unnecessary:
- **Only affected cases.** A case is re-timed if any function it can reach changed. placemat compares the two binaries' machine code per function, masking call and branch targets and data references (page/offset pairs such as arm64's `adrp`), which move whenever unpinned code or data moves. Reachability comes from the call graph, not only the stored hot set, plus a short fresh profile of the change's build to catch newly hot functions. Changes to data or read-only data with identical code, and changes to the allocation sequence, select every case that touches them, or all cases when that cannot be told. A random sample of skipped cases is spot-checked every time. (Selection needs a profile with one set per case, `placemat pin profile`; `placemat check --affected PROFILE` builds the stock binaries, selects the cases and times only those, plus a spot-check of the rest (`--spot`, default 10%). `placemat affected` does the machine-code comparison, call-graph reachability, profile edges and the spot-check today; data sections are compared too: a change in the size of any data section, or in the contents of string or plain data, selects every case, while constant data that differs at the same size selects every case when no function moved, and only warns when code moved (moving code changes it). The fresh profile and detecting allocation-sequence changes are planned: select all cases by hand when the allocation sequence changes.) On a typical change we expect 200 cases to become 10-30 (an estimate; P005). A subset also changes each case's predecessors, and so its heap history (§5.4); saying so in `check`'s report is planned.
- **Only the axes still open.** With colouring built into both arms, the data axis is skipped (chosen by hand today with `--data none`; detecting it is planned). A change that leaves the binary unchanged (scripts in the project's own language, docs, tests) skips the code axis (planned: today every placemat run varies the code).
- **Few variants.** Pinned and coloured builds have small spread, so most cases should stop at the first batch (`placemat check` today stops every case there): 8 pads of one variant each when the data axis is skipped (colouring built in), 4 pads otherwise. The project may lower the start where its spreads are known to be small.
- **One base for many arms.** Several candidates are timed against one base in the same rounds.

*What the steady state's interval means:* with pinned code, the code axis moves only the unpinned (cold) code, so the interval covers that pinned layout, not all layouts. Reports should say so (planned; today the geometry table's "unmoved" share, over all functions, shows how much of each arm stayed put, including anything linked before the pad); they never call the result layout-independent.

*Output:* the change's effect per affected case with an interval, the stock-layout result next to it, and a short list of anything that needs the full treatment (planned) (a case flagged layout-sensitive despite pinning, a hot function that moved). *Cost:* minutes (an estimate: 10-20 min for a typical change on Amber; to be measured, P005).

Without fixes, the steady state is a normal paired run of all cases at the stock layout (the *screening pass*; planned: no command times only the stock builds yet), then the full design on the cases it flags. Placement can hide a real change in the screening pass, so audits (§3.4) re-run everything.

### 3.4 Audit: the long version, now and then

Fixes cover what the survey saw. They decay, and they can hide new problems. An audit is the survey again, on the fixed builds and on stock builds, run periodically and whenever a drift detector fires. Things it exists to catch:

- **Hot-set drift:** the program's time moves into functions that are not in the order file (new features, new benchmarks, a refactor that renamed or split a hot function). Pinning then covers less of what matters, silently.
- **Stale profile data:** pads are regenerated on every build (§6.3; planned), but the hot spans and hot loops they protect come from the stored profile; when a hot function's code changes, its sampled offsets go stale and the pads protect the wrong spans.
- **What the steady state skipped:** cases its selection judged unaffected, and real changes the screening pass missed because placement hid them.
- **New classes of data problem:** a new allocation path that skips colouring; buffers below the colouring threshold that now matter; or a placement assumption nobody knew about. Our own example: the Amber prototype's first data axis coloured in 16-byte steps; that broke Amber's 32-byte alignment assumption (its allocator guarantees 64) and produced a false 25-35% "data effect" on two kernels ([colouring-report.md](amber-validation/colouring-report.md) §1). Only a wider look found it, and only knowing the project's alignment guarantee explained it. Audits should vary what the fixes hold fixed, within the project's guarantees, precisely to find such things.
- **Platform change:** a new compiler or linker version (flags that silently stop working: Apple's linker ignores unknown `-mllvm` options), a new CPU with different boundaries or cache geometry.
- **The fixes' own cost:** pads and colouring take space and a few instructions; an audit re-times stock against fixed builds so their cost and benefit stay known.

An audit on pinned builds needs a data axis that does not move the pinned code. Options, in order: the project's own colouring, when it has one; placemat's interposer, for projects on the system allocator, or its colouring allocator, for projects with an allocator API (linked after the code under study, but it can still move it: in Lua's hooked builds ([examples/lua/SURVEY.md](../examples/lua/SURVEY.md)) `__text` started 232 B later because the load commands grew, so build the order file and pads with it in, as for the hook); or, for a custom allocator without colouring (Amber today), compile the hook into **both** pinned arms and build the order file and pads with the hook in, so the pinned layout is the hooked one. An added hook grows the allocator and moves pinned code (Amber's did), which is why it cannot simply be switched on in a pinned build. And in a hooked build, the stock data setting (0, off) is not the shipped code, so every audit also times the true stock builds (§5.3). placemat builds the stock slot without the hook but with the arm's order file and pin pads; when the pads were planned with the hook in, the stock build's pinned region is therefore not the planned one: with `--pin`, every build (the stock build included) plans its own pin pads, so this does not arise; with fixed pads, check it with `placemat pin verify`.

*Cheap drift detectors* (planned, apart from `placemat pin verify` and the projects' own assertion builds; an audit today is a `placemat survey` run by hand), run with the steady state, decide when an audit is due:
1. **Hot-set coverage:** the stored profile's share of samples inside the order file, recomputed from a short profile of the current build; below a threshold (e.g. 90%), audit and regenerate.
2. **Placement check:** pin pads are regenerated on every pinned build (§6.3, `--pin`); the check (run after every link) then confirms the ordered functions are in order and aligned and that no hot loop or entry span crosses a boundary. A failure means the link did not place the order (missing or misplaced symbols) or the pad search could not satisfy the rule (a function grew past its slack): note it and audit.
3. **Alignment check:** the project's own alignment assertions (Amber: a `-DAMBER_ALIGNCHECK` build) on a coloured build.
4. **Instruction counts** (where available, P006/P007): a case whose instruction count changed but whose time did not, or the reverse, is worth a look.
5. **Anomalies:** a steady-state check that flags a case as layout-sensitive despite pinning.

*Cadence:* per release, after toolchain or hardware changes, and when a detector fires. Its results become the new survey baseline.

## 4. Architecture

```
placemat (Python, standard library only)
├── core
│   ├── design      layout variants: code pads, data colours and steps (§5)
│   ├── runner      rounds, arms, anchors, adaptive stopping, raw-data store
│   ├── stats       estimators, intervals, permutation tests, FDR (§5.7)
│   ├── analysis    per-case estimates, flags, verdicts and attribution (§5.7)
│   ├── report      Markdown and JSON; re-analysis from raw data; twospeed; inventory
│   └── config, lock  placemat.toml; the machine lock and noise probe
├── adapters
│   ├── bench       name/value lines; Google Benchmark and hyperfine JSON; K out[] scripts (§8.1)
│   ├── build       the build protocol: flags, pad source, order file (§8.2)
│   ├── code        source pads; lld --shuffle-sections (on .text*; planned)
│   └── data        malloc interposer; colouring allocator for allocator APIs; hook header for custom allocators (§7)
├── binary          Mach-O and ELF: symbols, loops, boundary crossings, per-function diffs; culprits; affected-case selection
├── pin             profile import, hot-set choice, ordering, pad search, verification (§6.3); strategy comparison (§6.4)
└── cli             run · survey · check · reanalyse · culprits · twospeed · inventory · noiselog · affected · design · binary · pin (fix and audit: planned)
```

The project supplies a small configuration file (`placemat.toml`): how to build with extra flags, how to run the benchmarks, the benchmark suites (with case names where a format cannot list them; the cases to time are given with `--cases`), the platform's boundary (`boundary`, default 4 KB), the data unit (`unit`: never finer than the project's alignment guarantee), the spans and the colouring threshold, the lock and noise probe, and the thresholds (format: `placemat/config.py`'s docstring). Recording which fixes are in place is planned, as are the suite options `isolation`, `reorderable` and `keep_prefix` (§5.4).

Implementation stays standard-library Python, as the Amber tooling is: no dependencies to install on a CI runner. Python 3.11 or later, for `tomllib`. Native pieces are small C files: the pad function source (generated by placemat, compiled by the project's build) and the interposer (compiled by placemat), and the hook header and colouring allocator (compiled by the project's build).

## 5. The experiment design

### 5.1 Levels and pairing

A **round** runs every layout variant of the current batch, for every arm, in a fresh random order; within a variant, the base and each change run back to back, in random order (randomised multiple interleaved trials, Abedi & Brecht 2017). Per-round ratios against the base are paired contrasts, which block out machine drift; shuffling the variants within each round keeps drift inside a batch from lining up with any one pad. Within an execution a case is timed at its iteration count; for cases under ~1 ms per iteration placemat times a geometric series of iteration counts and takes the regression slope (as Haskell's Criterion library does), falling back to the full-count time if the fit fails (a negative slope once lost a whole run); only suites whose harness honours the series do this (`series = true`; the default for K `out[]` scripts). Today (as in the Amber stage) each batch runs 7 rounds after one discarded execution of each binary and data setting. Reports already print Kalibera & Jones's dimensioning advice (rounds per pad from the variance components); planned (P005): choose rounds per pad (the level below the top) by Kalibera & Jones's dimensioning formula once a first batch has estimated the variance components; the number of pads, the top level, is set by the precision wanted (adaptive stopping, §5.7). Executions at a data setting also record a run covariate from the hook's or wrapper's log: by default the ASLR region base under the hook, and a hash of the k values in allocation order under the colouring allocator or the interposer, each categorised as "the most common value or not"; the stock slot, and placemat runs with the data axis skipped, have none. A covariate whose values do not repeat (its most common value seen fewer than 3 times or in under a fifth of the executions) is reported as unavailable, and no run test is made. Each batch's timing also starts with a noise probe (§11 item 3), recorded with the run. Placement drawn per execution (the region lottery, §5.4) is repeated by the iterations inside one execution, not resampled, so rounds are the lever; keeping each case's predecessors the same in every batch, recording the warm-up executions' bases and a stack-offset covariate are planned (§5.4, §5.5).

### 5.2 Code axis

- **Source pads** (portable): an unused function of P bytes, kept by `__attribute__((used))`, placed before the code under study. On Amber it sits at the top of the first source file in link order; under LTO, "linked first" alone does not fix where a function lands, so placemat checks every pad build's symbols (the pad present and followed by at least its size; a warning if many functions precede it), and adapters can check that it precedes the code under study (§8.2). Sizes come from a golden-ratio sequence, P_j = 64·⌊64·frac(u + j/φ)⌋ + 4·((7j + v) mod 16), with seeds u ∈ [0, 1) and integer v ∈ [0, 16), derived from a run seed (default 0, the Amber stage's; give `--seed` to vary it) and recorded. The sequence spreads the pads over the 4 KB period and the 64-byte phase at once. With seed 0 (`random.Random(0)` gives u ≈ 0.844 and v = 13), 12 pads have a largest gap of 620 B against 341 for even spacing, and cover 12 of 16 phases mod 64 and all 4 mod 16. placemat draws the seeds from one run seed with Python's `random.Random` in Amber's order (u and w₂ by `random()`, then v by `randrange(16)`; then w₁ by `random()`, where Amber drew its fallback z; planned: w₃ for stack offsets after w₁, §5.5), so seed 0 reproduces Amber's pads, and its steps in linear mode (hashed seeds are new). The phases hold only when functions are at most 4-byte aligned (clang on arm64): what moves the code is the pad function's footprint (P plus its own few bytes, rounded up to the next function's alignment), so with 16-byte function alignment (gcc -O2 on aarch64; any `-falign-functions=16` build) the pads move code in 16-byte steps and phases below 16 are not varied. The R2 sequence was rejected (its first coordinate is near 3/4, so pads cluster).
- **lld** (Linux): `--shuffle-sections`, which takes a section glob, so it can be limited to `.text*` and keep code and data separable. `--randomize-section-padding` (lld 20) pads code and data sections alike (`.text*`, `.rodata`, `.data`, `.data.rel.ro`, `.bss`) with no filter, as merged (llvm PR #117653), so it mixes data movement into the code axis; use it only as a combined layout axis, or if a later lld adds a filter (check before relying on either). Source pads remain the portable code axis. Record the resulting addresses either way.
- **Boundaries** are platform parameters: 4 KB on Apple M2 for small loops and hot entry spans (measured on Amber); Lua's interpreter also showed a 2-5% effect of its dispatch function's address mod 8, which the pads vary but the pin rule does not check (`-falign-functions=16` freezes it); 32/64-byte fetch windows and 4 KB on x86 (to be measured, P006).

### 5.3 Data axis

Large allocations (default ≥64 KB) can be moved in two independent ways, and placemat supports both:

- **Colour:** one constant offset c for every coloured allocation. It moves the data relative to things that stay put: page and huge-page boundaries (hardware prefetchers commonly stop at a page boundary; split accesses; TLB reach), uncoloured allocations, static data and the stack. It does not change coloured buffers' offsets relative to each other.
- **Step:** each block gets its own offset, varying coloured buffers' offsets relative to each other, which decides their L1 set conflicts. Hashed (default) or linear, below. (A step also moves block 0, so a step contrast is relative *plus* some absolute movement.)

**What k is.** For measurement, k is derived from the block's *position*, not from allocation order. The allocator knows its own structure, so under the hook it passes k: the prototype hook validated on Amber used the block's slot index within its region (its offset from the region base divided by the block size). The interposer works it out: k = ⌊(address − base) / G⌋, with base the first coloured block's address in the process and G one fixed granule for the process (the smallest coloured size); floor division and a non-negative mod, since mappings can lie below the base (glibc places them top-down). A raw address would carry the ASLR slide into k. Even with a per-process base, an allocator that randomises each large mapping separately makes k vary from run to run; each data method's log carries a hash of the execution's k values in allocation order (individual k values at `PLACEMAT_ADDRLOG=2`), and the run test's covariate summarises them coarsely enough to repeat across executions (for example, whether a hash of the k values in allocation order matches the arm's most common one; under hashed steps the k values themselves, not only their gaps, decide the placement); when nothing repeats, the run covariate is reported as unavailable (§5.1). k repeats across executions only while the heap history before the block is fixed (§5.4).

**Linear and hashed steps.** A linear step s·(k+1) (Amber's validated form, with √2 steps) spreads blocks one to a few slots apart well, but it has two limits. It is periodic: the relative offset depends only on Δk mod (span_s/unit), so blocks 256 slots apart (at 16 KB and 64 B) share their offset at every step. And k must be on one scale for all blocks: if each block's k is its slot index in its own size class (Amber's prototype hook) or its address divided by its own size (an interposer using per-block divisors), a 64 KB block and a 1 MB block can share a k, and no step ever moves one relative to the other: exactly the mix of a window and a table workspace in zstd's one-shot compression (the caller's input against the workspace). So placemat's general form is a **hashed step**: k is the block's offset from the base divided by one fixed granule for the whole process (the smallest coloured size, default 64 KB), and block k's step offset is unit·(H(seed_j ⊕ k) mod (span_s/unit)), with H a mixing hash and seed_j the variant's step seed. Every pair of blocks then gets a pseudo-random relative offset in each variant, whatever their sizes and distance. The linear form stays available as an option for any project (with k on the same fixed-granule scale); no project gets a different k rule. An allocator calling the hook should pass k on that same scale, preferably from the header's `placemat_k()` helper, which does the signed floor division before casting to the unsigned type (doing it in unsigned arithmetic would give blocks below the base a k that no longer matches Python's re-analysis): k = ⌊(address − base) / G⌋ with one base for the whole process (its first region's base, or the first coloured block's address), never a base per region (blocks at the same offset in different regions would then share k) and never the raw address (which would bring back the ASLR lottery).

**Offsets and spans.** Block k's offset is (c mod span_c) plus its step offset (hashed by default, or linear (s·(k+1)) mod span_s), in whole units: unit = the cache line (64 B by default; never finer than the project's alignment guarantee); span_s = the L1 set stride (16 KB on M2; 4 KB on typical x86); span_c up to the page size or beyond (e.g. 2 MB for huge-page effects), as configured (placemat's configuration defaults both spans to 16 KB on every platform, which is four pages where pages are 4 KB). Under the hook the memory cost is small (offsets come from a block's spare room; with the growth rule a vector can move up a class a little early); under the interposer or the colouring allocator each coloured block is over-allocated by a header, alignment, span_c and span_s (2 MB on a 64 KB block is 32×, so large colour spans suit only projects whose coloured blocks are large or few). A project can vary colours only, steps only, or both.

**Which matters** depends on the allocator. Amber's buddy allocator aligns every large block to its own size, so all large buffers shared one offset mod 16 KB: their problem was relative, and its validation used steps only (a colour there moves every large block equally and leaves their conflicts unchanged). An allocator that already scatters large blocks, or a workload sensitive to page boundaries or to its position relative to small allocations, needs colours. Address logging (§7; today by running a hooked build by hand, since a survey keeps no block logs) says which of colour and step a project needs; the default is both. Where the regions themselves land, and which block of a region a buffer gets, are the subject of §5.4 (on Amber the window kernels' speed also depended on the region's base, above the page).

**Design.** Pads, colours and steps come from one Kronecker sequence (a low-discrepancy sequence: multiples of irrational numbers, mod 1) with independent generators (pads in 4-byte steps as in §5.2; colours in whole units and never zero; linear steps likewise never zero, while a hashed step gives each block its own offset, 0 for about 1 block in span_s/unit):
- pad P_j as in §5.2 (generator 1/φ);
- step: hashed mode, seed_j = ⌊2⁶⁴·frac(w₂ + j·√2)⌋ (computed in double precision, so its low bits are zero) and block k's step offset unit·(H(seed_j ⊕ k) mod (span_s/unit)), with H the splitmix64 finaliser including its golden-gamma add, H(x) = mix(x + 0x9E3779B97F4A7C15) with mix(z) = z ⊕ (z ≫ 30), ×0xBF58476D1CE4E5B9, ⊕ (≫ 27), ×0x94D049BB133111EB, ⊕ (≫ 31), all mod 2⁶⁴, and k taken mod 2⁶⁴ (two's complement) before hashing, so the hook, the interposer (whose k can be negative) and Python re-analysis compute identical offsets; linear mode, s_j = unit·⌊(span_s/unit)·frac(w₂ + j·√2)⌋, replaced by one unit if it comes out 0, and block k's offset (s_j·(k+1)) mod span_s (√2 as in Amber's validated stage, where 2s and 3s stay spread: blocks used together are often 1-3 slots apart);
- colour c_j = unit·⌊(span_c/unit)·frac(w₁ + j·√3)⌋, likewise never 0;
with seeds w₁, w₂ ∈ [0, 1) recorded per run. Each pad is timed at the stock setting (0, off), at (c_j, off) and at (0, step_j), where step_j is seed_j (hashed) or s_j (linear): no extra builds (one build per pad per arm), half again as much timing as stock plus one data setting (Amber's two per pad), and a separate colour contrast and step contrast per pad. The code test uses the stock-setting variants. A project that varies only one of the two times two settings per pad, as Amber did. Fitting colour and step jointly (one setting per pad, then a regression) is not reliable: the effects live in narrow windows (an aliasing window is a line or two wide in 16 KB), not along a line in c or s; it is listed as exploratory (§11).

**The stock build.** Under a hook, (0, off) is the hooked build with no offset, not the shipped binary (the hook adds code); under the colouring allocator or the interposer it is not the stock placement either (§7). So the stock builds (no hook, colouring allocator or interposer) of both arms are timed as one more slot in the first batch, and the reports say which placement each figure is at.

### 5.4 Heap placement: regions and history

Two things besides the data setting decide where a large buffer lands: where the allocator's regions land in the process (the **region lottery**: address randomisation draws it per execution), and which block of a region the buffer gets (**heap history**: what the process allocated and freed before it). The data axis offsets blocks within whatever placement these two give. The run covariate records the lottery's draw (§5.1), and the analysis uses it (§5.7); pairing the draw between arms, holding the history fixed, varying it on purpose and fingerprinting it are planned (§13). The evidence behind this section is in [amber-validation/heap-and-stack.md](amber-validation/heap-and-stack.md).

**What they do.** On Amber (M2, one thread) the window kernels' speed is a repeatable function of the region's base. s_msum100 ran at 23.2 ms at the stock setting when the region landed at 0x300000000, as it does in about half of all executions, and at 8.5-24 ms elsewhere; at the stepped setting it ran at 8.4 ms at any base, since steps give the blocks new relative offsets. The bases fall into three populations: 0x300000000 itself; a cluster at 0x604000 mod 8 MB (about a fifth of executions), never slow; and a low range just above the program's image and first mappings (about a third), rarely repeating and carrying most of the remaining spread. A base's time repeats across executions and runs (to ±0.5 ms at 0x300000000, 3-7% in the low range), although every base is at least 16 KB-aligned and every large payload sits at the same offset mod 16 KB: the L1 set indices are the same at every base, so the mechanism lies above the page, in structures indexed by virtual address (TLBs and page-walk caches, prefetchers are the candidates), not yet explained. The 8 MB spacing suggests placement against a boundary that moves in 8 MB steps, possibly the main thread's stack, which would tie the lottery to §5.5. The lottery belongs to the platform, not to Amber: a plain program mapping 1 GB on macOS arm64 lands at 0x300000000 in about 45% of executions and otherwise in the same 8 MB-spaced cluster and low range (`scripts/probes/run.py`). History matters too: Amber's chains.k window cases were 1.25-1.5× slow in 7-13 of 20 whole-script processes against at most 1 of 20 fresh ones (the script's set-up and one case), and once slow a process stayed slow in every repetition, its temporaries coming back from the same free blocks; a build with Amber's own colouring was never slow. How history and the lottery combine is open (§11 item 13).

**What follows for the design.** The execution carries this variance (§5.1), and the cases in one execution share its draws, so they err together, a group of them showing a false *change* at once in a few percent of runs (§5.7). The history is fixed within a placemat run only when the allocator and program are deterministic and single-threaded and each case runs after the same predecessors; a per-process hash seed, threads (§5.8), or an allocator that randomises large mappings separately (macOS's malloc for medium and large blocks) make it vary.

**Pairing the lottery** (the hook). The hook asks the project's allocator to map its first large region at a hint (`PLACEMAT_REGION_HINT`) drawn per round and pad, the same for both arms and every slot of that pad, so every base's effect cancels in the paired ratio and the within-pad contrasts (colour, step, isolation, stack) are paired on base too; pads stay independent units for the t interval, and the code test and the anchors, which compare across pads, still rely on §5.7's standardisation. Pairs of executions at 0x300000000 have a paired log-ratio standard deviation of 0.02-0.04, against 0.26-0.46 for pairs at other, generally different, bases; low-range bases repeat only within 3-7%, so hinted pairs there are noisier.
- **Which hints:** drawn from the bases this machine produces unhinted (a calibration run of the project's own build, kept per machine), so the mix stays natural and a hinted (0, off) stays the stock placement for §5.7's attribution. The estimand is the effect at a common natural mix, conditional on the calibration's mix (its sampling error, about 0.5 points on a change that removes a lottery and none in a null run, is added to the interval or the condition stated). Hints are absolute addresses; the main image's address (the slide) and `argv`'s address are logged beside the base, and hinted executions at a base must reproduce the natural time at that base, or hints are given relative to the slide instead.
- **How:** only the first anonymous region; macOS `mach_vm_allocate` with `VM_FLAGS_FIXED`, which fails safely; Linux `MAP_FIXED_NOREPLACE`, never `MAP_FIXED` (ignored before 4.17, so the returned address is always checked). A refused hint falls back to the natural base, which the log records. Refusals are not random: low-range hints collide with each execution's own image and early mappings most often, in the population that carries the variance, so refusal rates and paired spreads are reported per population.
- **Unhinted rounds:** a whole number of each batch's timed rounds (two of seven, say) stays unhinted, with the warm-up executions §5.1 discards (their bases recorded), to give each arm's share of the bases, Fisher's test of the arms against the base categories, and the arm-specific estimate (§5.7); under hints, s (§5.7) is their share (or the calibration's), not the hinted executions', which are the design's own draw and biased by refusals; the paired estimate uses the hinted rounds only.
- **Limits:** only the hook can hint (the colouring allocator and the interposer get their blocks from the system allocator), and the stock slot, built without the hook, keeps its lottery: for a lottery-heavy case its result and the stock-code-layout attribution need many more rounds (hundreds on Amber's windows: minutes of timing), which the report should state rather than calling the result noise (planned); on Linux the runner could read the stock slot's base from `/proc/<pid>/maps`.

**Holding the history fixed.** Every batch and anchor runs each case after the same predecessors: cases that precede a still-running case keep running in later batches, their results discarded (`[[suite]] keep_prefix`, the default for suites whose cases share an execution), and a dropped case's line becomes a comment of the same length (`bench.k_subset`), so the script's size does not change either. `check` runs subsets and keeps no prefix (it would undo §3.3's saving); its report says that its history differs from the survey's.

**Varying the history** (surveys and audits):
- **Isolation:** `[[suite]] isolation = "case"` runs each case in its own execution after the suite's set-up (the default, `"script"`, runs the suite in one); `placemat survey --isolation` adds a contrast-only slot per pad, its stock setting under case isolation, flagged like colour and step (family *isolation*). An isolated case also starts with cold caches and predictors and fresh mappings, so a flag says "depends on running after the others", and the fingerprint says whether placement is why. Cost: one execution per case per pad, arm and round, each repeating the set-up, so a survey times it on a subset of cases.
- **Case order:** one order per (round, pad), shared by that pad's slots and both arms and recorded, so pairs and within-pad contrasts share their history and the t interval over pads carries the variance of drawing orders (the code test is left unpaired on order, as with hints; the stock slot takes pad 0's order; with `keep_prefix` the prefix is taken in the round's order). The k hash then stops repeating, and a group sharing an execution still errs together. Off by default; a suite allows it with `[[suite]] reorderable`, and placemat can reorder a `k-out` script's `out[]` lines itself when all set-up precedes the first case.
- **Repetitions in place** (iterations) stay the harness's business; placemat does not add them for precision on placement-sensitive cases, since they repeat the placement.

**The fingerprint** (for explanation, not adjustment): per execution, the full addresses of the large blocks with their sizes and offsets within their regions, the region bases and the slide; per case, the blocks allocated during it and those live at its start. The analysis looks for the address bits and distances between mappings that separate slow executions from fast ones: the data analogue of the code culprits (§5.6, §6.2). It needs the block log (`PLACEMAT_ADDRLOG=2`) kept for every execution, with a per-case limit in place of today's 4,096-event cap, and **case marks**: the harness calls `placemat_mark(index)` before each case (a C call, or a primitive the project's adapter adds for script harnesses), which every data method writes into its block log in order with the blocks. The harness takes it as a weak reference with a null check (or through `dlsym`), so a build without a data method skips it, and in the stock slot's script the calls become comments of the same length. Marks cannot be encoded as allocations of a magic size: the hook logs only large blocks, a smaller sentinel would need a check on the small-block fast path (§7 forbids it), and a sentinel's first use of a size class would change the history it observes.

### 5.5 Stack placement

Where the stack starts, and so where every frame, spill slot and local array sits, depends on the bytes of arguments and environment the kernel copies above it at exec (on macOS also the `apple[]` strings, which carry random values and the executable's inode) and on the stack's randomisation; Mytkowicz et al. (2009) moved results by several percent by changing only the environment's size. The colour setting already moves large heap blocks relative to the stack, so what only a stack factor varies is the stack against code, static data and small heap blocks: the alignment of stack arrays and spills against cache lines, their L1 sets against hot heap buffers, and on Intel x86 loads falsely depending on stores 4 KB apart. None of this is built or measured yet (§13).

- **Platform first.** Whether the stack is a factor placemat can set or a random one it can only record depends on the platform: Linux's `arch_align_stack` subtracts a random amount below 8 KB on x86-64 (and, to be confirmed, below a page on arm64), so under Linux address randomisation the offset mod 4 KB is already uniform per execution; on macOS arm64 it is not randomised within a page (argv's offset mod 4 KB takes two values per environment size, the `apple[]` strings' random lengths, and moves in 8-byte steps with the environment's size), so there the environment sets it. `scripts/probes/run.py` measures this per platform (and runs on Linux x86-64 and arm64 in CI, scripts/README.md). A small C program reporting `argv`'s address (set by the block above the stack) and a local's address in `main`, mod 64 B, 4 KB and 16 KB, over many executions per environment size, gives the jitter per size on each platform.
- **Hold the block constant.** placemat's own environment and paths must not move the stack between slots, as they otherwise would: the stock slot gets none of the data method's six to eight variables, `PLACEMAT_CASES` changes between batches, and the binary's path carries the pad's tag (`p76-h` against `p3508-h`), so the initial stack pointer differs by about 290 bytes between the stock slot and the others and by tens between settings and pads, confounding the stock-build comparison (and so the "stock code layout" attribution), the colour and step contrasts and the code axis with stack shifts. `PLACEMAT_STACK_PAD`, set per execution to a per-machine target size minus everything else above the stack (strings and their 8-byte pointers: `PLACEMAT_CASES`, `PLACEMAT_SERIES`, the script path in `argv`, the inherited variables, the binary's path), makes that block constant, in every slot including the stock slot (whose stack is then no longer exactly the shipped one, which reports say). The pad absorbs differences in names, values and path lengths by itself, so values are not zero-padded (a project hook reading them with `strtoul(…, 0)` would take them as octal); the target is the reference length (the stack slots' baseline, below) plus the largest stack offset, so every offset is reachable by shortening the pad. On a `[target]` children start under `env -i`, since the ssh layer adds variables of varying length. macOS's `apple[]` strings vary per execution, so there the goal is the same distribution in every slot; the data methods' constructors log `argv`'s address as a check, and in the stock slot the harness's own report of it, where it can give one.
- **Record:** the initial stack offset mod the L1 set stride, logged per execution as a second run covariate and reported, not used to adjust: a randomised offset does not repeat, and its effect is expected to be cliff-shaped rather than smooth.
- **Vary,** where the offset is not randomised within a page: the pad's length moves the stack pointer in 16-byte steps with no build change. Each pad gets a contrast-only stack slot, its stock setting at offset o_j = 16·⌊(span_s/16)·frac(w₃ + j·√7)⌋ for all its rounds and both arms, every other slot running at the reference length (√7, not √5: √5 = 1 + 2/φ would tie the offsets to the pads' generator; w₃ is drawn after w₁, §5.2). The family *stack* flags heterogeneity across the o_j (the spread of the per-pad contrasts, permuted among pads within a round, assuming pads exchangeable within a round as the code test does; it also picks up an interaction of code layout and stack); the mean contrast against the reference is reported but not flagged, since it could flag the reference (as Lua's `tbl_array` colour flag described the colouring wrapper's own (0, off), §7). `placemat survey --stack` turns it on. Where the offset is randomised, the covariate is the tool; turning randomisation off (Linux `setarch -R`; macOS's private `posix_spawn` flag) freezes the stack and the heap regions together, which suits pairing, not estimation. A start-up shim that allocates a designed amount of stack before `main` is the fallback if the environment cannot reach the offsets needed (it needs a build change and moves code).
- **Limits:** a program that copies its environment to the heap gets a different heap history from a longer pad (Amber's K runtime to be checked); other threads' stacks are placed by the thread library, so the stack factor covers the main thread only. Fixes, if a project turns out stack-sensitive, are the project's (realigned or padded frames, `-mstackrealign`).

### 5.6 Targeted variants

Rare bad layouts (a 64-byte loop crosses 4 KB in ~1.5% of positions) are missed by any modest sample. For flagged cases, `culprits` lists the loops that cross only in slow variants and the share of layouts in which they cross; placemat then adds pads inside and outside each window and reports a weighted average and a worst case. The data analogue would use logged buffer addresses (§7; no tool reads them yet). Today `placemat culprits` lists the loops and suggests pads inside and just outside each window, and they are timed by hand with `placemat run --pads`; automating this is open (§11 item 5). `culprits` looks only for small backward-branch loops: an interpreter whose hot path is indirect dispatch within one large function (Lua's computed-goto handlers) has none, and its placement effect showed instead as the function's address phase (mod 8) in the Lua survey.

### 5.7 Statistics and verdicts

- **Effect:** per layout variant, the median over rounds of the paired ratio; per pad, the geometric mean of its variants, weighted equally (with three variants the offset settings carry 2/3 of the weight, against 1/2 in Amber's two-variant stage: a deliberate change of estimand, §10); the effect is the geometric mean over the m pads with a t interval over pads, m − 1 degrees of freedom (Kalibera & Jones's equation 4 at the build level). A pad's variants share a code layout, so pads, not variants, are the independent units. Also reported over each data setting alone (stock, coloured, stepped). The case is marked **colour-dependent** when the coloured result differs from the stock-setting one, and **step-dependent** when the stepped one does (each a paired t over pads at p < 0.01 divided by the number of offset settings compared (0.005 each when both vary, 0.01 when one does), and by more than the threshold; this needs 99.75% t quantiles, which the Amber stage did not tabulate); either makes it *data-dependent*.
- **Sensitivity**, tested per arm (base and each change separately), then combined: a case's p-value is the smaller of the two, doubled (with more arms, the smallest times the number of arms):
  - **Code:** using the stock-setting variants only (so data effects cannot raise code flags), permute pad labels within a batch's rounds (the anchor included); statistic the within-batch sum of squares of trimmed means (medians' range saturates under permutation). The code spread is likewise the range of the stock-setting variants' medians. Assumes those variants are exchangeable within a round.
  - **Data:** two sign-flip tests, one for colour (each pad's stock-setting variant against its coloured one) and one for step (against its stepped one), each flipping the two labels *within rounds*; statistic the sum over pads of the squared per-contrast t. Flipping within rounds, not over pads, keeps the smallest attainable p far below the false-discovery threshold even with few pads (over pads alone it would be 2^(1−m), too coarse for Benjamini-Hochberg (BH) correction across hundreds of cases). Assumes a pad's two variants are exchangeable within a round.
  - **Run:** the region lottery's draw (the region base, as "the most common base over all executions, or not") or another per-execution covariate, by a max-|z| permutation test over the kinds of data setting (stock, coloured, stepped), the variants as strata within a kind and the anchors in the stock kind; grouping per pad's colour or step seed instead would leave groups of one variant, whose 7 executions allow at most 35 labellings and floor each arm's p near 1/35 whatever the effect. Where a covariate is available, every execution, anchors included, is **standardised** to the natural mix: log y' = log y − δ̂·(I − s), with δ the covariate's effect per arm and kind, estimated within variants, I = 1 at the pooled mode, and s the mode's share pooled over both arms and all layout variants (the base depends neither on the data setting nor on the pad); for a covariate that depends on the arm's own allocations (the hash of k values) each arm is standardised to its own share and mode, which reduces variance but cannot correct an imbalance; contrast-only slots get their own δ̂ or none. The code, colour and step tests, the anchors' scaling and the disturbed-round detector use the standardised times, whenever a covariate exists rather than on a trigger (an adjustment switched on by the run test's p changes the estimand between replicate runs near the threshold), and the unstandardised results are reported beside them. Each arm's share of the categories and Fisher's exact test of arm against category are reported, and both estimates, at the common natural mix and at each arm's own mix (per-base effects reweighted by the arm's shares): a real change can move the base distribution (a larger binary, other mappings), and the test only warns. (Built today: one group per pad's colour or step seed, anchors excluded, each arm against its own mode; post-stratification by `strat_ratio` switches on at p < 0.05; §13.)
- **Location estimator** (planned; §11 item 16): chosen once, for every case and run, by estimand invariance and by its calibration under arm swaps (Honesty, below): the mean of log ratios estimates the geometric mean at the natural mix of region bases with or without the run covariate's standardisation, while the median jumps between modes under a multimodal lottery (a change that removes a lottery reads about −54% as the median of the two-speed mixture and about −51% at the natural mix); the mean is less precise under heavy tails, and the standardised median is overconfident (82-87% coverage on Amber's window cases), so it is excluded. The median stays until the choice is made, the standardised mean reported beside it once standardisation exists; once a standardised estimator is used, its interval adds, in quadrature, the standardisation's error that does not average out over pads, Σ_K w_K²·[(s_b,K − s)²·SE(δ̂_b,K)² + (s_a,K − s)²·SE(δ̂_a,K)²] + (Σ_K w_K·(δ̂_b,K − δ̂_a,K))²·SE(ŝ)², with w_K the per-pad weight of kind K and s_x,K arm x's share among its layout variants of kind K (0.1-0.6% on Amber's windows).
- **Flags:** Benjamini-Hochberg across cases (q = 0.05) separately per family (code, colour, step, run), and also p ≤ 0.01 and an effect over the project's threshold (default 3%; 10% for cases whose base time for a whole timed sample is under 5 ms). The effect, per family: the code spread (range of the stock-setting variants' medians); the largest per-pad |coloured/stock − 1| or |stepped/stock − 1|; or the largest per-setting effect of the run covariate. The isolation and stack contrasts (§5.4, §5.5; planned) are flagged the same way, the stack family on heterogeneity across offsets. BH alone is not enough with coarse permutation p-values: one shared disturbance gave five cases the same tied p ≈ 0.03, and BH rejected all five.
- **Adaptive stopping:** batches are counted in **pads**, so a pad's variants are always timed in the same batch (the code test runs within batches and the data contrasts within rounds): start with 4 pads, add 2 at a time until the interval's half-width is under the target (default 1%) or a cap of 12 pads when each pad has two or three variants; with one variant per pad (data axis skipped), start with 8 pads, add 4, cap 24, as Amber's `--no-data` runs did, so the t interval keeps enough degrees of freedom; stop on width only, never on significance. A pad has 1, 2 or 3 variants (data axis skipped; colour or step only; both), so a first batch is 8, 8 or 12 variants (Amber counted 8 → 24 variants in both its modes: 4 → 12 pads with data, 8 → 24 pads without). Each later batch also re-times pad 0's stock-setting variant as an **anchor**. Drift between batches already cancels in the paired ratios, so the anchor is used only to put later batches' absolute times on the first batch's scale (for the code test's ranges), never to rescale ratios: dividing ratios by one noisy anchor would correlate the pads and break the t interval. (Amber: drift between batches reached 5%.)
- **Verdicts** (checked in this order): *change* (the interval of the ratio excludes 1, i.e. no change, and the effect exceeds the threshold); *placement* (the stock builds' own paired result is measurable, meaning its interval, a percentile bootstrap over rounds with 4,000 resamples as in the Amber stage, excludes 1 and it exceeds the threshold, and the case is not a change; or the case is flagged for code, data, run, isolation or stack sensitivity: the combined flag, the smallest per-arm p times the number of arms against the largest per-arm effect; per-arm flags are reported but do not set the verdict); otherwise *noise*. When the stock builds' measurable result has an interval that misses the stock-setting variants' interval, the difference is attributed to the **stock code layout** when (0, off) is the stock placement (a hook whose no-offset setting places blocks as the stock allocator does, or no data axis at all), since the two then differ in code only; otherwise (the colouring allocator, the interposer, or a hook that changes placement) to the **stock build**, code or placement undistinguished. Any verdict can carry the qualifier *data-dependent* (above).
- **Honesty:** coverage under adaptive stopping is only approximately nominal (Amber's two null runs of the prototype, 52 cases each: 7 of 104 intervals missed 1 (no change), 6.7% against 5%, consistent with that); no minimum-time estimator (under perturbation it would pick the luckiest layout); exchangeability of pads within a batch is an assumption, stated in reports; and main against main is not a perfect null when base and branch are separate directory arms (git arms of one revision share one tree and one set of binaries). The code test's statistic (sum of squares of trimmed means) loses power when whole rounds are disturbed: on a noisy machine the Lua survey's 2-5% code effect was missed by it and found by a within-round rank test (open, §11). Calibration is checked by **arm swaps** (planned as `placemat reanalyse --swaps N`; the figures below come from scratch re-analyses, [amber-validation/heap-and-stack.md](amber-validation/heap-and-stack.md) §2.5): on a null run whose arms share binaries, swapping the arm labels within each (variant, round) pair, the same swap for every case in an execution, gives the exact null distribution of the whole analysis (given the realised pad counts), and so its coverage, its randomisation standard deviation and its false-*change* rate per case and per run. On Amber's null runs (§10) coverage was 95.3% and 95.5% over 52 cases and 94-95% on the window cases; but cases sharing an execution err together, so a group with a large run-level lottery shows a false *change* in a few percent of runs (about 6% for Amber's window group, 3.6-4.0% with the standardised mean), and every case's calibrated interval excludes 1 in about 5% of null runs however narrow it is.

### 5.8 Threaded benchmarks

Design only (P011); every timing so far ran single-threaded (Amber with `AMBER_THREADS=1`). Some projects time multi-threaded code: Amber 2.6.0 spreads big vectors over all cores by default, and zstd has a multi-threaded compressor. Threads add variation that layout variants do not control:

- **Thread count is part of the case.** Each execution runs at one thread count T, passed to the harness as `PLACEMAT_THREADS` (the project maps it, e.g. to `AMBER_THREADS`); cases at several counts run in separate executions. A case is reported as `name[T=4]` when T is set, and as `name` otherwise (not `name@T`: the K adapter already uses `@` for a series' iteration counts). Recommended counts: T = 1 for attribution, where placement effects are clearest; T = the number of performance cores for threaded behaviour; the project's default (all cores) only as an experiment of its own.
- **Heterogeneous cores.** On Apple M2 (4 performance and 4 efficiency cores), work split evenly over eight threads finishes when the slowest thread does, so the efficiency cores are stragglers, and which threads land on which cores varies from execution to execution: a placement effect in one thread can be hidden, or appear only sometimes. macOS offers no thread affinity, only QoS classes (a background QoS confines a process to the efficiency cores: controllable, but not representative). Linux has affinity (`sched_setaffinity`, `taskset`, cpusets), so there placemat would fix the core set per execution (control); whether to vary it as a designed factor is open (§11). On macOS, T no larger than the performance cores and a quiet machine reduce the effect but do not remove it.
- **Core placement as a run covariate.** A candidate is the share of the child's CPU time spent on performance cores, which does not depend on wall time (macOS: whether `proc_pid_rusage` reports time per core type is to be checked; Linux: the core each thread ran on, or none needed under affinity). The child's CPU time over (wall time × T), taken per child with `wait4`, is cheaper, but wall time is the response itself, so it can only be a diagnostic, never an adjustment; and it is per execution, not per case. The performance-core share would be a second run covariate beside the ASLR base or the k hash (one per placemat run today; a third with the planned stack offset, §5.5, a joint scheme being open, §11 item 15); CPU time over (wall time × T) can only be reported.
- **Quiet machine.** The noise probe (§11 item 3) must run at the case's thread count: a single-threaded probe cannot tell whether T cores are free (how: open).
- **Data axis.** k is still computed from position (§5.3), but which buffer gets which k, and so which offset, can depend on scheduling: per-thread free lists or arenas (Amber's allocator keeps per-thread free lists), and a base fixed by whichever thread allocates first. A data setting is then a distribution of placements, not one placement, and the colour and step contrasts average over it. Under the colouring allocator and the interposer the k values themselves can vary, not only their order, so the k hash rarely repeats and is reported as unavailable (§5.1). Steps act on each core's L1D; threads on cores of one cluster share its L2 (on M2, one per cluster), where a step changes only the low set-index bits; across clusters they share only the system-level cache. The efficiency cores' L1D is smaller (64 KB against 128 KB on M2), so a step span chosen for the performance cores may not match their set stride.
- **Statistics.** Unchanged in form; expect larger within-variant variance (more rounds per pad by Kalibera & Jones's dimensioning, §5.1) and two-speed rounds, which `placemat twospeed` shows (each round's time over its variant's median, as in §10 (e)).

## 6. Code: measurement and pinning

### 6.1 Binary analysis

Per binary: symbols with addresses and sizes; small loops (backward branches within ≤256 B) and whether they cross the boundary; hot entry spans from the profile; per-function machine-code equality between two builds (for the steady state's affected-case selection). Mach-O and ELF (arm64, x86-64): symbol tables read directly; code disassembled with `otool -tV`, or `objdump`/`llvm-objdump`. Tested on Amber (Mach-O), in a Linux arm64 VM, and on cross-built x86-64 ELF.

### 6.2 Culprits

For a layout-sensitive case: the small loops that cross the boundary in every slow stock-setting variant and in no fast one (only hot-set functions' loops with `--hot`), with the share of all layouts in which any of them crosses. It is Mytkowicz's causal analysis applied to loops. Before the loops, the address phase: whether the slow pads' code shifts fall in phases mod 2^k (4 up to the period) that the fast pads' do not. The statistic is the number of pads the best phase rule misplaces; its permutation p is over splits of the same pads into as many slow and fast (exact up to 20,000 splits), corrected over the moduli by Westfall-Young min-p, and only a corrected p ≤ 0.05 is called an alignment effect (m ≤ 64) or a position effect. When even a perfect split could not reach that (one slow pad of four; as many phases as pads), culprits says "too few pads to tell" (Lua 5.4.6's `fib`: 6 of 12 pads slow, all at 4 mod 8, corrected p 0.002; Amber a2's `dictplus`: one slow pad of four, too few). Pads are compared within their batch, each against pad 0 or the batch's anchor in the same rounds, so a slow batch is not read as slow pads. Without the run's binaries, the phase still comes from the raw file and the loops are skipped.

### 6.3 Pinning

1. **Profile** the benchmark set; attribute samples by address (macOS `sample` strips LTO suffixes and lumps stubs into the last function).
2. **Hot set:** functions in order of combined share until each benchmark set reaches ~95% of in-binary samples.
3. **Order:** C3-style clustering behind heaviest callers, clusters capped (16 KB), sorted by density.
4. **Link:** ld64 `-order_file` or lld `--symbol-ordering-file` (GNU ld `--section-ordering-file`), plus `-falign-functions=16`: ld64 keeps each function's address mod 16 from the LTO object, and most functions there are 4-aligned at arbitrary offsets, so reordered functions drift by −64 to +16 bytes: an order file alone pins only to within ~64 bytes. What ld64 preserves depends on the input's section alignment: on Amber 2.7.2 it kept every function's address mod 64, so pads planned in 16-byte steps left 39 hot loops across 4 KB and 64-byte steps cleared them (another session's finding, 2026-10-06). Set `[build] pin_align` (passed as `PLACEMAT_ALIGN`) to what the linker preserves; the check after every link reports pads that landed elsewhere. On ELF, placemat passes `-Wl,-z,separate-code` to pinned links in `PLACEMAT_LDFLAGS`: without it lld puts `.text` straight after `.rodata` and `.eh_frame`, which grow with the pin pads, and moved the ordered region off its plan in 2 of 6 test builds.
5. **Pads:** pad functions listed in the order file, sized by an exact search over the start address mod the boundary that minimises a weighted cost (Amber's `pads.py`: 10⁶ per small-loop crossing in a listed function, 10⁴ per hot-entry-span crossing, 1 per pad byte; this is the rule used for Amber's recommended pinned build; a variant adding 10³ per 64-byte-line crossing of a function's hottest loop to the loop-only rule (build D, against C) gave no consistent gain (`placemat pin pads` uses these weights, and the line term only when given `--hot64`)). Loop crossings are effectively forbidden; since any start mod 4096 costs at most 4,080 pad bytes, a hot-span crossing survives only when avoiding it would make a loop cross, and the verification step reports any that remain.
6. **Verify:** symbols present and in order (`placemat pin verify`, with `--plan PLAN.json` for a manual build; never trust the linker's silence: a build script may discard its warnings), no crossings, then time (§3.2).
7. **Regenerate** pin pads on every build (they belong to the build, not the source): `placemat run --pin NAME=ORDER [--pin-spans NAME=FILE]` links each build once without pin pads, plans them at that build's position, links again and verifies against the plan; a build whose functions are not at the plan's offsets fails and is not used. Fixed pads (`--order` with `--pin-source`) remain available; having no plan, they are checked only for order, contiguity and alignment, as warnings.

### 6.4 Comparing ordering strategies (P009)

The order in step 3 is a choice. placemat can build several and compare them on the project (`placemat pin compare`): by hotness, by density, Pettis-Hansen, C3/hfsort, and random order as a control (hfsort+, CDSort and per-benchmark clusters are planned). Each pinned layout freezes its own luck (on Amber several pinned builds (B16, C, D) had a few cases 5-10% faster or slower than their layout-averaged speed), so a strategy is never judged from one build: the whole ordered region is shifted through designed offsets (a pad in front of it over the 4 KB period and the 64-byte phase, in 16-byte steps since pinned builds align functions to 16), with the pin pads planned afresh at every shift (`--pin`), so each strategy is measured at its best (computing them once and shifting them with the region, as the first Amber comparison did, lets a shift bring crossings back), and averaged like any comparison (`placemat run --pad-first`). `placemat pin compare` reports, per strategy, the static measures (text and pad bytes; profile-weighted 4 KB and 16 KB pages spanned by hot code; crossings before padding); the measured ones (layout-averaged speed against stock; spread; per-case winners and losers) come from the multi-arm run's report (on Amber: [examples/amber/P009.md](../examples/amber/P009.md)).

## 7. Data: colouring for measurement and for real

Three ways to colour, depending on who owns the allocator:

- **Interposer** (projects on the system allocator): a small shared library loaded with `DYLD_INSERT_LIBRARIES` / `LD_PRELOAD` that offsets allocations at or above the threshold. To keep size class and wrapper overhead the same at every data setting, it over-allocates by span_c + span_s and adds its header in *every* variant, (0, off) included. Its (0, off) is therefore *not* the stock placement (the header shifts the payload, and large blocks from the system allocator are page-aligned on macOS (on glibc they start 16 B into a page)), so under the interposer "code measured at the real placement" holds only approximately; the true stock builds (no interposer) are timed as one more slot in the first batch, and reports say which placement each figure is at. As built (`placemat/data/interpose.c`, `placemat_alloc.c`): each large block it returns carries a 32-byte header and is recorded in a set of the blocks it returned; it passes every other pointer (allocated before it loaded, or inside the C library) to the real functions; a large `realloc` moves the payload to the block's new offset; `malloc_usable_size`/`malloc_size` report the requested size; an alignment above the unit is honoured by rounding the offset down (counted as wrapped). Limits: macOS's `malloc_zone_*` functions are not interposed (SQLite's default allocator uses them), and SIP-protected binaries, and hardened-runtime ones without the allow-dyld-environment-variables entitlement, ignore `DYLD_INSERT_LIBRARIES`; a report warns when no block was coloured at any data setting.
- **Colouring allocator** (projects with a pluggable allocator API, such as zstd's `ZSTD_customMem`, SQLite's `SQLITE_CONFIG_MALLOC` or Lua's `lua_Alloc`): placemat's colouring allocator (`placemat_alloc.c`, the interposer's core), compiled into every pad build of every arm when the data axis is varied (as the hook is: the build gets `PLACEMAT_HOOK=1`), never into the stock builds, and installed through the project's API (`[data] method = "allocator"`; Lua's example, and zstd's survey null run, predate that method and spell it `method = "hook"` with `stock_placement = false` and `covariate = "khash"`, which is equivalent). Link it after the code under study; even then it can shift that code (in Lua's builds, larger load commands moved `__text` by 232 B), so in a pinned build it needs the same care as the hook (§3.4). Like the interposer it over-allocates and adds its header at every data setting, so its (0, off) is not the stock placement either, and colour or step flags can describe the wrapper's own (0, off) rather than the project: Lua's `tbl_array` was colour- and step-flagged (about −11%) because only (0, off), with its payload at a page plus 64 B, was slow, while the true stock build ran like the offset settings. The report should set the stock builds beside (0, off) and the offset settings and say which the stock build resembles (planned). It colours exactly what goes through the API (the project's heap, and any harness buffers the adapter routes through it), and it works where the interposer cannot: SQLite's default allocator on macOS calls `malloc_zone_malloc`, which the interposer does not intercept.
- **Hook header** (custom allocators): interposing `mmap` does not help an allocator that aligns blocks internally (Amber's buddy allocator put every payload ≥64 KB at the same offset mod 16 KB however its region moved). The project includes `placemat.h` under a flag (`-DPLACEMAT_HOOK`); without the flag the binary is unchanged.

```c
/* placemat.h (sketch) */
size_t placemat_k(const void *block);              /* k for a block: signed floor((address - base) / G), then cast */
size_t placemat_colour(size_t k, size_t size, size_t spare_room); /* offset for block k (from placemat_k, §5.3) */
void   placemat_log_alloc(const void *p, size_t size);  /* address logging for diagnostics */
void   placemat_log_free(const void *p);
/* environment: PLACEMAT_COLOUR (constant offset c), PLACEMAT_STEP_MODE (hashed | linear),
   PLACEMAT_STEP_SEED (hashed: seed_j) or PLACEMAT_STEP (linear: step s); with neither set, no step is applied
   (a seed of 0 is a valid step, not "off"); setting both, or the one that does not match PLACEMAT_STEP_MODE,
   is an error at start-up,
   PLACEMAT_UNIT (granularity, default 64), PLACEMAT_COLOUR_SPAN (default the page size),
   PLACEMAT_STEP_SPAN (should be the L1 set stride; the header's default is 16384, M2's, so set it elsewhere),
   PLACEMAT_MIN (smallest coloured size, default 65536), PLACEMAT_ADDRLOG (0, 1 = regions, 2 = regions and blocks),
   PLACEMAT_LOG (the summary file).
   Block k's offset is (c mod colour_span) + its step offset: unit*(splitmix64(seed ^ k) mod (step_span/unit))
   when hashed, (s*(k+1)) mod step_span when linear; k on one fixed granule from one per-process base (§5.3);
   when the block has less spare room, the offset is wrapped modulo the largest whole number of units
   that fits (0 below one unit). Wrapping keeps offsets spread rather than piling every short block on one
   value, but a wrapped block no longer has the variant's exact colour or step. Every block of at least PLACEMAT_MIN is
   counted ('coloured', at every setting, (0, off) included), and wrapped ones separately, in a summary appended at exit to PLACEMAT_LOG (the file the runner
   reads); at PLACEMAT_ADDRLOG=2 the first 4,096 block and free events (address, size, k, offset) are kept too. The
   report flags a run in which more than 10% of coloured blocks were wrapped (per variant, and counting
   offset settings only: planned). The full API, also placemat_active(), placemat_region() and
   placemat_log_block(), is in placemat/data/placemat.h. */
```

Planned additions to the header: `PLACEMAT_REGION_HINT` (the first large region mapped at a hint, §5.4); and, with the colouring allocator and the interposer, `placemat_mark()` (case marks, §5.4) and logs of the program's slide and `argv`'s address (§5.4, §5.5).

Rules the allocator side must keep (learnt on Amber): take the colour from existing spare room so size classes don't change; undo it on free so free lists never see coloured blocks; keep the small-block fast path untouched (an extra check on every allocation cost allocation-bound cases 3-10% until it moved out of line); keep growth points (a vector growing one item at a time must still move up a class once per class, at most a little early, never re-copying within a class); preserve the alignment guarantee, and check it with the project's own assertion build.

The same hook doubles as the shape of a project's *real* fix: if a project adopts colouring (as Amber may, with its own per-allocation steps), its choice can defer to `placemat_colour()` under the flag, so placemat can still vary it. Valgrind client requests can sit under the same flag (P004, P006).

Address logging (`PLACEMAT_ADDRLOG=2`, from running a hooked build by hand: the runner logs regions only and discards each log once read; keeping block logs from a survey is planned) answers the survey's first data question. Large buffers can sit at fixed offsets (a hidden bias: every run gets the same placement, good or bad; Amber's sat at the same offset mod 16 KB in every execution and every code pad), move with ASLR (the region lottery, §5.4), or move with code pads (then the two axes are confounded unless data is controlled).

## 8. Interfaces

### 8.1 Benchmark protocol

A benchmark command prints one line per case and iteration count: `name value iterations [unit]`, the value being the total time for that many iterations, in µs unless a unit is given (ns, us, ms or s); tab-separated when names hold spaces. placemat passes, per execution:
- `PLACEMAT_CASES`: the cases to run (others may be skipped);
- `PLACEMAT_SERIES`: for the regression series, a list of scale factors per case (e.g. `msum100=0.125,0.25,0.5,1`); the harness runs each listed case at each scale within the same execution, after a discarded warm-up, so scale is not confounded with rounds or ASLR. Cases not listed run once at their own count.
- `PLACEMAT_STACK_PAD`: padding that holds the block of arguments and environment above the stack constant, which harnesses ignore (§5.5; planned).

A harness that can calls `placemat_mark(index)` before each case (§5.4; planned).
Adapters translate existing formats: Google Benchmark JSON, hyperfine JSON, and K scripts of `out["name";reps;{...}]` lines (Amber's). A harness that cannot skip cases or scale iterations still works, at higher cost.

### 8.2 Build protocol

Two ways in, because build systems differ:
1. **A compiler wrapper** (`[build] mode = "cc"`, `placemat/cc.py`; the P010 adapters use item 2 through build scripts): placemat sets `CC`/`CXX` (and the linker driver) to `placemat-cc`, which adds the variant's flags, compiles the generated pad source into the link, and passes the order file. This works with make, CMake, Meson and most others without changes, as long as the build honours `CC`. For build systems that pin their own compiler (cargo, Bazel), a project adapter is needed.
2. **Environment variables** for build scripts that read them (the reference is `placemat/build.py`'s docstring): `PLACEMAT_SRC` (the arm's tree), `PLACEMAT_OUT` (a fresh output directory), `PLACEMAT_WORK` (kept per arm, for incremental builds), `PLACEMAT_VARIANT` (a tag), `PLACEMAT_PAD` and `PLACEMAT_PAD_SOURCE` (the code-axis pad's size and a generated C file holding it; unset for the stock build), `PLACEMAT_HOOK=1` (hooked builds) and `PLACEMAT_INCLUDE` (the directory of `placemat.h`, set for every build), `PLACEMAT_CFLAGS`, `PLACEMAT_LDFLAGS`, and for a pinned arm `PLACEMAT_ORDER_FILE`, `PLACEMAT_PIN_SOURCE` (its pin pads, named in the order file) and `PLACEMAT_ALIGN` (the function alignment the pin pads assume, `[build] pin_align`, default 16).
Either way, the build must leave the binary at a configured path, and placemat checks every pad build after linking: the pad function must be present (it can be dead-stripped despite `used`, P006; a build without it fails), and the next function must start at least the pad's size after it (a warning in the report otherwise). For a pinned arm, placemat also checks after every link that the ordered functions (the pad first, with `--pad-first`) are present, in order, contiguous and aligned (`placemat.pin.verify`; a warning in the report otherwise); adapters may check more themselves (the Lua adapter checks that the pad precedes all of Lua). Builds are cached by the arm's tree (a git revision, or the files matching `[build] inputs`), the build command and environment, the adapter's scripts (the config directory's, every file the build command names by path and the scripts beside it, and `{config_dir}`/`{root}` patterns in `[build] inputs`; paths inside a `sh -c` string are not seen), placemat's data sources, the pad, the hook, the pinning, and the platform the build runs on (OS and architecture, of the `[target]` with its prefix when one is set); a variant usually needs one small object recompiled and a relink. Every execution gets the same block of arguments and environment above the stack, held constant by `PLACEMAT_STACK_PAD`, and on a `[target]` children start under `env -i` (§5.5; planned).

### 8.3 Outputs

Every run keeps its raw timings (JSON, written after every round and batch, marked incomplete until the end, so a crash keeps what was timed; an unfinished batch's rounds are kept but not analysed), with epoch times per batch, per round and per timed execution, and the noise record's samples over the run (P012), so verdicts can be recomputed with new statistics without re-timing (`placemat reanalyse`). Reports: a Markdown summary (verdict per case, intervals, stock-layout result, spreads and flags; a per-arm summary; and "if placement were ignored": the range of results a one-build-per-arm comparison could have reported from this run's pads, how many cases could have shown a false change or missed a real one, and the most layout-dependent cases) and the JSON behind it; code culprits come from `placemat culprits RAW CASE` while the run's binaries exist. Reports also mark noisy batches beside the disturbed rounds: a batch whose gate went ahead after its wait, whose end probe was over `max_noise`, or whose noise-record samples had a median spread over it (P012); qualify a colour or step flag "on one pad" when its largest pad gives at least half the sign-flip statistic while the typical effect is under the threshold (the flag rule is unchanged); and give the dimensioning advice an F-test p for the pad variance, saying "cannot advise" when it is not significantly above 0 and taking the cost of a pad from build time without lock waits. Also from raw timings: `placemat twospeed` (run-to-run switching between two speeds) and `placemat inventory` (which runs were timed with the noise probe gating, §11 item 3). The raw file also keeps the region hints and refusals, the slide and `argv`'s address, case marks and block logs, the warm-up executions' bases and the case-order seeds, and reports give standardised results beside unstandardised ones, both mixes' estimates, and arm-swap rates (`placemat reanalyse --swaps N`) (§5.4, §5.5, §5.7; planned).

- **(d) the pinned build against main,** data axis skipped (the stored pads were computed without the hook, which would move pinned code; or rebuild the order file and pads with the hook in), with the targeted pads only ([inputs/targeted-pads.txt](amber-validation/inputs/targeted-pads.txt); cap 8 pads, so no designed pads are added: the default adaptive run would add up to 16 designed pads for setdictbig's wide interval, a different and three times longer test), over two runs. The five cases main flags for code in the reference (setdictbig, setdictbigall, setdictbigname, chargrade, takekeys10x10): main code-flagged, and the pinned arm *not flagged* per arm (p ≤ 0.01 with BH, over the threshold), with a pinned spread well below main's (reference: setdictbig 2× on main against 3.9% pinned, at a per-arm p of about 0.05 in the quiet run and 0.2 in the loaded one, so it passes only by the flag rule; chargrade +33% against 2-3%). The other three cases (grade, fsum, sc_member) are controls, expected flat in both arms at these pads (sc_member was +35% code-sensitive on main in the order-file runs, at other pads). The Markdown report gives each arm's code p and flag, and `examples/amber/check.py` reads the JSON's per-arm flags. Designed pads alone may leave a pinned case or two weakly code-sensitive (the reference saw tillists at 4.5%); that is reported, not failed. One of the two reference runs was heavily loaded (load 7.03 at the end), so a rerun of this check should be quiet.
- **(e) the coloured build** (data axis skipped, as in the reference, since the build colours itself): for msum100, mavg100 and mdev100 (and the bench-std msum/mavg/mdev cases), the run-to-run p90/p10 ratio (each round's time over its variant's median, pooled over variants; [tools/col-twospeed.py](amber-validation/tools/col-twospeed.py)) falls from 1.4-2.6 on main to at most about 1.15; mmin and mmax, unaffected by placement, stay at most about 1.17 in both.
The runs are named by criterion and replicate: a1, a2 main against main (52 cases); b1, b2 the placement-slowdown branch against its base; c11, c12 main against main on win.k's windows; c21, c22 the window prototype against its base; d1, d2 pinned against main; e1, e2 the coloured build against main. Their results are in [PROGRESS.md](PROGRESS.md); restating (a) and (c) is open (§11 item 18). A verdict outside these criteria is a finding to explain, not automatically a regression: the general rules were partly designed to fix weaknesses the Amber prototype had (for example, linear steps over per-class slots could not separate blocks of different sizes).

## 11. Open questions

1. **Boundaries off Apple Silicon:** which code boundaries matter on x86-64 and on other arm64 cores (P006).
2. **Interposer details:** the functions and ownership rules are decided (§7); open are C++ `operator new` on platforms where it does not go through malloc, and programs that mix `malloc_zone_*` and `malloc` on one block (macOS).
3. **Lock and quiet machine:** placemat takes a user-supplied lock command (in the project config, or in a machine overlay named by `PLACEMAT_MACHINE`, whose `[machine]`, `[target]` and data spans override every project's: one project config then serves several machines), and can wait for the load average to fall (`[machine] max_load`) and for a noise probe to come out steady (`max_noise`; both off by default). It waits before taking the lock, so a waiting timing run does not block other people's work; once it holds the lock it checks again, and if the machine is noisy it releases the lock and tries again later, going ahead (and saying so) after `wait` seconds. (A lock command may have its own wait: Amber's `pbt/quiet.py` waits up to 30 minutes for load < 3 while holding the lock.) The probe is a single-threaded pure-Python loop (~14 ms) timed 21 times in placemat's own process (or, with a `[target]`, in the target through its prefix, with its own baseline); its spread is 1.2 × (q75 − q25) / median, the interquartile range scaled to the old measure (second-largest − second-smallest of nine, still recorded as `spread_old`) on a quiet M2, so that one or two stalled timings no longer fail it (P012: on a quiet M2 the old measure's worst readings reached 15%, the new one's 8%). The gate needs two passing readings in a row, 5 s apart, before timing (re-checked under the lock), and records for each batch its epoch start, the passing streak, whether it went ahead, both spreads, the probe time, the wait and the load, and the end-of-batch spread. `placemat noiselog` keeps a continuous record (one reading a minute, about 0.3 s of one core, without the lock) in `~/.cache/placemat/noise.jsonl`, which runs keep and reports join to each batch; the example configurations gate at `max_noise` = 10% (which also lets the probe's level run to 20% over its usual time), leaving the record and the per-batch marks (§8.3) to carry the rest. The lock command runs under a guard that ends it (and its process group) when placemat lets go or dies, so a killed run leaves no waiter holding the machine lock. The machine counts as quiet when the spread is at most `max_noise` and the probe's median is within 1 + 2 × `max_noise` of this machine's usual probe time (the 10th percentile of its last 200 readings, kept in `~/.cache/placemat/probe.json`): a spread alone misses a uniformly slow machine (the Lua survey had a batch run about 35% slow while the probe's spread passed). It is run and recorded at the start and end of every batch, so a run whose batches started or ended noisy says so; a disturbance inside a batch is not seen (the Lua survey had rounds 4-7 of one batch 20-40% slow, missed, giving false code flags). Reports now detect disturbed rounds from the timings themselves (rounds in which the median slot ran more than 10% over its lower quartile), since a disturbance slows every slot at once; the rank test (§11 item 10) is robust to them. The detector works on standardised times (§5.7) and ignores the slots without a run covariate for run-flagged cases, since the region lottery otherwise reads as a slow machine (planned). Open: the probe's threshold and workload per platform; how to run it at the benchmark's thread count (§5.8); and what to recommend on shared machines (on a loaded M2 a fixed 15 ms CPU loop varied by 10-20% before the probe existed, and the old probe's worst quiet readings were 5-15%; efficiency-core scheduling is a plausible cause, not yet shown).
4. **Run-level perturbation:** varying environment size (hyperfine, Mytkowicz) as a third axis is designed as the stack factor (§5.5), and the region lottery and heap history as factors placemat records, pairs or varies (§5.4); what remains open is in items 13-17.
5. **Automated targeted variants** (§5.6) and their weighting.
6. **Hashed steps:** they give every pair of blocks a pseudo-random relative offset, but lose the low-discrepancy coverage per pair that linear √2 steps give neighbours; validate on zstd (window plus tables) against linear steps.
7. **Exploratory: one data setting per pad with both colour and step,** split afterwards by regression on (c, s) or on features from logged addresses (which buffers share sets; which cross page boundaries). Unreliable as a default (effects sit in narrow windows), but it would halve the data-axis timing if it worked.
8. **Pinning back ends:** whether to offer BOLT or Propeller as alternatives to the order-file pipeline on Linux.
9. **Names:** whether "survey / fix / check / audit" are the right command names.
10. **The code test's statistic:** the within-batch sum of squares of trimmed means (§5.7) loses power when whole rounds are disturbed; the Lua survey's 2-5% code effect (the interpreter's address phase mod 8) was found by a within-round rank (Friedman-type) test and missed by it. Both are reported now (the rank test's p beside the flag's); whether to flag on the rank test is to be decided after the Amber re-validation, whose criteria were set with the current statistic.
11. **Culprits beyond small loops:** `placemat culprits` reports the address phase that separates slow pads from fast ones, with a permutation p over pads (§6.2; on Lua 5.4.6's `fib`: 4 mod 8 slow, 0 mod 8 fast, an alignment effect); naming the function responsible still needs the hot set.
12. **Threads** (§5.8, P011): how to time threaded cases on heterogeneous cores without affinity (macOS); whether, on Linux, core placement should be varied as a designed factor rather than only fixed; and which core-placement covariate is measurable on each platform.
13. **The region lottery's mechanism** above the page (§5.4): which virtually indexed structure; whether the stack's position decides the 8 MB-spaced bases; and how history combines with it (win.k's first case is slow in about half its executions with only set-up before it, yet chains.k's cases in fresh processes almost never are: history may decide whether a slow base matters, or one mechanism, speed set by the hot buffers' absolute addresses, covers both).
14. **The stack's randomisation per platform** (§5.5): measured first; it decides between a stack axis and a covariate.
15. **Two run covariates** (the region base and the stack offset): a joint scheme for testing and adjusting.
16. **The location estimator** (§5.7): the mean of log ratios (estimand-invariant) or a robust one, by arm swaps.
17. **Case order** (§5.4): whether it should ever be varied by default.
18. **Regression criteria (a) and (c)** (§10): (a) fails on code flags that look like real layout effects (all slow at one pad, alike in both identical arms): restate it as "no *change* verdicts; code flags only where both identical arms agree"? (c)'s main-against-main half fails on a false *change* (c12), which arm swaps show to be a tail draw of the region lottery: as written, (c) fails about 12-14% of run pairs whatever the method, and more as precision rises (the windows de-correlate). Options: restate it as "no *change* verdicts" with the swap-measured false-change rate beside it; keep it; a family-wise interval over the window group (failing at most about 10% of run pairs); or judge the method by arm swaps (coverage about 93% or more and a false-change rate under a stated bound, from 10,000 swaps); with any of these, a narrow *unresolved* verdict for run-flagged, unpaired cases whose interval excludes 1 but whose nearer bound lies inside the threshold (replacing only *change*, decided before *placement*; on its own it does not satisfy (c) as written). Rejected: confirming a change at the stepped setting (its premise holds only in null runs, and it changes the estimand); tightening the *change* rule for every case (power lost everywhere); an *unresolved* verdict for every case at the threshold (it would relabel 19 of 87 *change* verdicts so far, real 3-5% changes among them).

## 12. Claims and credits

As far as the survey found (PRIOR-ART.md §(a)), placemat can claim four things, each a combination or a gap rather than a new ingredient: designed joint code-and-data variants with per-case attribution and FDR control; colouring a custom allocator's large buffers as an experimental factor; the measure-pin-verify workflow; and (modestly) Apple Silicon support. It must not claim to be first at finding layout sensitivity, layout randomisation, multi-level designs, paired or interleaved runs, adaptive stopping, colouring, or order files, and must not claim a layout-independent speed. The README credits Mytkowicz et al. 2009, Curtsinger & Berger 2013, Kalibera & Jones 2013 (with Kalibera, Bulej & Tůma 2005 and Kalibera & Tůma 2006), Georges et al. 2007, Abedi & Brecht 2017, Laaber et al. 2020, Bonwick 1994, Kessler & Hill 1992, Afek, Dice & Morrison 2011, jemalloc, Rivera & Tseng 1998, Pettis & Hansen 1990, Ottoni & Maher 2017, Benjamini & Hochberg 1995, and the .NET 6 loop-alignment and Intel JCC-erratum guidance on boundary rules, and credits lld's `--shuffle-sections` (planned as the ELF code axis, limited to `.text*`) and `--randomize-section-padding` (which also moves data, so at most a combined axis) as related work; neither is used yet.
