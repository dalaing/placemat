# Heap placement beyond the data axis, and the stack: evidence and reasoning

The design draft for ISSUES.md P013 (heap history) and P014 (stack placement), 2026-10-07, after eleven cold reads; its design is folded into [DESIGN.md](../DESIGN.md) §5.4 and §5.5, which is authoritative. This file keeps the evidence (§2, re-derived from the Amber regression's raw files in `placemat-work/runs/`, kept outside the repository) and the reasoning behind each choice. Section numbers are this file's own unless prefixed "DESIGN". Nothing in it is built.

## 1. The question

DESIGN varies two things on purpose: where code sits (pads, DESIGN §5.2) and where large heap blocks sit relative to fixed things and to each other (colour and step, DESIGN §5.3). Everything else is "run": what differs between executions, summarised by one per-execution covariate (DESIGN §5.1). Three influences on placement are not designed today:

- **The region lottery:** where the allocator's regions land in each execution (address randomisation), which decides which pages, translations and higher-level cache sets the data meets.
- **Heap history:** which block, and so which offset within its region, each buffer gets, set by what the process allocated and freed before.
- **Stack placement:** where the stack starts, set by the bytes of arguments and environment above it and by the stack's randomisation.

## 2. What we have measured

### 2.1 The region lottery decided c12

Amber's re-validation runs c11 and c12 time main against itself on six window cases (`win.k`), both data offsets varied, 12 pads (DESIGN §10 (c)); re-read from the raw files, where each execution is stored as (time, region base the hook logged).

- **Two speeds by base.** For s_msum100, executions whose region landed at 0x300000000 (47-52% of executions, pooled per run; 40-63% per arm and setting) ran at a median 23.2-23.3 ms at the stock setting against about 16 ms at other bases, and 19.4-20.4 against 14.4-16.5 ms at the coloured setting; at the stepped setting the base made no difference (8.3-8.5 ms either way).
- **Three populations of bases.** Pooled over a1, a2, c11, c12, c21, c22, b1 and b2 (every execution with a logged base, all suites: 4,816) the bases fall into three disjoint groups: 0x300000000 itself (46.8%); a cluster from 0x11c604000 to 0x12b604000 (20.5%) in which every base is 0x604000 mod 8 MB, spaced in 8 MB steps and recurring; and a low range from 0x104be4000 to 0x109fac000 (32.7%) at 16 KB granularity, rarely repeating (646 distinct bases among 721 low-range executions in the c runs); nothing falls between 0x109fac000 and 0x11c604000. For s_msum100 at c12's stock setting: 0x300000000 23.2 ms (p10-p90 22.7-24.0); the 8 MB cluster 16.0 ms (13.2-16.6), never slow; the low range 16.5 ms (10.5-24.0), carrying nearly all the remaining spread. Times are a repeatable function of the base: in the 8 MB cluster 0x122604000 gave 13.2-14.2 ms in all four c runs, 0x125604000 15.5-16.6 ms (anchors included), 0x11ee04000 8.5-9.0 ms (the stepped setting's speed); the low range's few repeats agree within about 3-7% (22.4 and 23.2 ms; 8.3 and 8.9; 13.6 and 13.6), against ±0.5 ms at 0x300000000. So the binary "most common base or not" category leaves a spread, in the low range, as large as the gap it explains; a third category (the 8 MB cluster) explains only 1-19% of the remaining variance, so the binary covariate stands.
- **Above the page.** Every base is at least 16 KB-aligned (lowest set bit 14 or above; 0x300000000, the only 4 GB-aligned one, at bit 32), and Amber's buddy allocator puts every large payload at the same offset (64 B) mod 16 KB, so the base changes nothing in the L1 set index or the page offset. A recurring base gives times repeatable to within about ±0.5 ms (0x300000000) to ±1 ms (other bases) across executions that get fresh physical pages, which points to structures indexed by virtual address (TLBs and page-walk caches, prefetchers that learn on virtual addresses) rather than physically indexed cache sets: not yet explained. Since the L1 set indices are the same at every base, same-offset L1 set conflicts cannot be the whole mechanism either, which qualifies DESIGN §1's and §5.3's account of the window kernels ("every large buffer sat at the same offset mod 16 KB"; "step decides L1 set conflicts"). The populations suggest where the lottery comes from: the 8 MB congruence looks like top-down placement against a boundary that moves in 8 MB steps (a candidate is the main thread's stack and its guard, just below 0x170000000 on arm64 macOS: if so, the stack's randomisation co-decides the lottery, linking §2.1 to §4), the low range like bottom-up placement just above the program's image and its first mappings, and 0x300000000 like the fallback when neither fits. Alignment alone does not make a base slow: several other bases are 2 MB-aligned (0x105a00000, 0x107400000, 0x109600000 among them), and c12's main arm at 0x107400000 ran s_msum100 at 16.2 ms, the ordinary speed.
- **Not the cases before it.** s_msum100 is win.k's first case, with only the script's set-up before it, and it shows the full effect; the draws are independent across executions (no clustering by batch or round: permutation p 0.06-0.99; the arms of a pair draw alike in 48-52% of pairs, as chance gives).
- **What it did.** c12 reported a *change* between identical builds on five window cases (s_msum100 +4.8% (+1.1 to +8.7), s_mavg100 +5.7%, s_mdev100 +3.8%, s_mavg10 +5.7%, s_mavg1000 +4.8%), where c11 had −1.9% to −2.7% with intervals covering 1. The arms' shares of the slow base match the signs: in c12 the base arm drew it in 34 of its 84 stock-setting executions and main in 44 (main "slower"); in c11, 53 against 42. The window cases share executions, so the same draws moved all five: a chance imbalance in independent draws, amplified by a 1.45× effect.

### 2.2 Why the run test missed it, and what fixing it does

The run test (DESIGN §5.7) groups executions by data setting before its max-|z| permutation test, and `analysis._setting_key` makes the offset settings fine: one group for the stock setting (all 12 pads' stock-setting variants, 84 executions) and one per pad's colour and per pad's step seed (24 groups of one variant, 7 executions each). The stock group's z is large (7.7 for the base arm, 14.0 for main on c12's s_msum100), but a group of 7 executions has at most C(7,3) = 35 labellings, so a small group that carries a real effect (the coloured groups do; they set the observed maximum, 11.6 and 23.1) reproduces its own |z| under permutation with probability about 1/35: each arm's p-value is floored near 1/35 to a few thirty-fifths whatever the effect's size, and the reported run p, the smaller arm's doubled, near 2/35 ≈ 0.057, as observed (run p 0.053-0.21). The same floor applies wherever DESIGN §5.7's run test has a one-variant group.

Grouping by kind instead (stock, coloured, stepped, the variants as strata within a kind) gives a per-arm p of at most 0.0001 for every window case in both runs (effects: stock +28% to +59%, coloured +17% to +42%, stepped about 0), so both runs are run-flagged. What then to do about the estimate was tried three ways on these runs (scratch copies of the code, by the cold reads of this draft):

| analysis | c12 windows (identical builds) | c11 s_msum100 | c21 s_msum100 (real change) |
|---|---|---|---|
| today (per-pad groups, no adjustment) | +3.8% to +5.7%, all excluding 1: *change* | −2.3%, covering 1 | −54.1% |
| grouped by kind, then today's post-stratification (`strat_ratio`) | +1.3% to +2.2%, all covering 1 | covering 1 | −51.7% |
| the mean per variant, unstandardised | +5.3% (+2.2 to +8.5) on s_msum100: *change* | −3.4% (−6.6 to −0.1): a false *change* | −51.6% |
| grouped by kind, each execution standardised to the natural mix of bases, median pipeline unchanged | +1.7% to +3.1%, all excluding 1 (s_mavg10 still a *change*) | −3.0% (−5.8 to −0.2): a new false *change* | −50.9% |
| grouped by kind, standardised, the mean of the standardised log ratios per variant, the standardisation's error added (a candidate, §3.2 item 2) | +1.7% to +3.0% (s_msum100 +2.89% (+0.23 to +5.61); s_mdev100 +1.67% (−0.09 to +3.46)); s_mavg10 +3.04% (+0.32 to +5.84), at the threshold | −1.7% to −2.3% on the windows, no false change | −50.8% |

Today's post-stratification covering 1 on c12 is luck rather than design: its half-width (2.9 points) is wider than the standardised mean's (2.7) and its centre 0.7 points lower, and §3.2 rejects it on other grounds. Measured over arm swaps (§2.5) on c11 and c12's five windows: today's analysis covers no change in 94-95% of swaps with a false *change* in 6.0-6.7% of runs; the standardised mean covers 94-96% with 3.6-4.0%; the unstandardised mean 95-96% with 5.0-5.1%; the standardised *median* only 82-87%, with 10.3-10.8%. No re-analysis removes the lottery's variance, for three reasons:
- **The binary covariate removes only the slow mode's imbalance.** Executions at 0x300000000 are tight (s_msum100 at the stock setting: 23.2 ms, a standard deviation of 0.02 in log), but the other bases run from about 9 to 25 ms (0.2-0.3 in log), almost all of it in the low range (§2.1: the 8 MB cluster is never slow), and their own chance imbalance between the arms is a sizeable part of the original excursion (within variants, main against base among the other bases: +2.5% to +8.7% at c12's stock setting, depending on how the comparison is made): §2.1's three populations. Paired on the exact base the noise disappears: s_msum100 pairs whose arms both drew 0x300000000 have a paired log-ratio standard deviation of 0.020-0.039, pairs both at some other base 0.26-0.46, about the same as mixed pairs (0.37-0.47).
- **Medians on standardised data are overconfident.** Standardising collapses the slow-base executions to a spike, and the per-variant median of 7 paired ratios locks onto it: on c12 s_msum100 the median-based interval is ±1.3% against ±2.7% for a mean-based one on the same data, and its coverage over arm swaps is 82-87%.
- **The estimand moves.** A change that removes the lottery (c21's prototype) is worth −54.1% as the median of a two-speed mixture and about −51% at the natural mix (the unstandardised mean-based figure is −51.6%), a move of 2-3 times the interval's half-width. Post-stratification as built also gives up the round pairing and weights categories by the smaller count, not the natural shares.

The analyses also changed the flags. Today's post-stratification code-flags the c12 windows, because the anchors enter the code test unadjusted while the pads are adjusted; standardising every execution, anchors included, removes those (the code spread falls from 60-88% in the base arm and 46-70% in main to 3-13%). The colour flags that appear are real: at 0x300000000 the coloured setting runs 17% faster than stock (19.3 against 23.3 ms, c12 base arm), at other bases 10% (13.95 against 15.54 ms), about 13% at the natural mix, which the unadjusted analysis's noise hid; criteria (a) and (c) allow colour flags. The windows were step-flagged already.

### 2.3 The anchors and the stock slot take the lottery too

Each later batch re-times pad 0's stock setting as its anchor, 7 executions, of which 1-5 drew the slow base in c12; a batch's scale can flip by about 1.45×, which likely drives c12's 60-88% (base arm) and 46-70% (main) "code spreads" on the windows and the false code flags above. The lottery also fools the disturbed-round detector: in each of the six rounds c12's report lists as disturbed (+10% to +22%), the stepped slots sit at their lower quartile (+0 to +2%) while the stock and coloured slots run +36% to +42%: most base-sensitive slots happened to draw 0x300000000, not the machine slowing down. The stock slot runs the stock build, which has no hook and so no covariate (and no region hint, §3.3): its intervals on these cases are ±40-50% (c12 s_msum100: −51.4% to +43.8%), so the stock-pair route to a *placement* verdict and the "stock code layout" attribution have no power for them (flag-based *placement* is unaffected), unless it gets many more rounds: its paired log-ratio's standard deviation is 0.23-0.57 on the windows, so a ±3% interval takes some 230-1,500 rounds for a mean-type estimate (1.96·σ/0.03 with σ from 0.23 to 0.59 on the windows; more for today's bootstrap of a median under a bimodal lottery), about 1.5-10 minutes of timing on win.k (0.2 s per execution, two arms) and 6-40 minutes on a 52-case suite (0.8 s per execution): costly but feasible.

### 2.4 Heap history

The amber-fusion work (`amber-fusion/planning/fusion-phaseb.md`, "Heap history, not the first repetition"; Amber on M2 with `AMBER_THREADS=1`, 20 rounds) timed chains.k's sliding-window cases (bench_rolling, and its suite and std msum, mavg and mdev cases) three ways. They ran 1.25-1.5× slower in 7-13 of 20 processes when the whole script ran in one process, and in at most 1 of 20 when each case ran in a fresh process holding only the script's set-up and that case (first repetition included). Once slow, slow throughout: every slow first repetition was followed by slow repetitions 2-5 (13 of 13, 11 of 11), as a repetition's temporaries come back from the same free blocks. The fusion work's PC build (its order file plus Amber's colouring) was never slow (0 of 20). That run logged no region bases. The two results do not fit a lottery that ignores history: win.k's first case, with only set-up before it, is slow in about half its executions, yet chains.k's cases in fresh processes (set-up plus one case) were slow in at most 1 of 20. So in chains.k the history seems to decide whether a slow base matters (an interaction), unless the harnesses differ in something else (set-up allocations, buffer sizes, the Amber version); reconciling them comes first among the timed experiments (§3.8). A simple hypothesis covers both: speed depends on the hot buffers' absolute addresses (region base plus offset within the region); in win.k the offsets are fixed, because the history is, so only the base varies, while fresh chains.k processes give the buffers other offsets. The fingerprint's full addresses (§3.5) test it directly.

### 2.5 How often it misleads

Over every identical-build run so far (15 runs, 336 case comparisons: Amber a1, a2, c11, c12; the SQLite, zstd and Lua null runs on the Mac and in the Linux VM), the 95% layout-averaged interval excluded 1 in 19 (5.7%, nominal 5%), and all 5 *change* verdicts are c12's windows.

An exact check is available. In a1, a2, c11 and c12 both arms are the same binaries (one tree) and the order within a pair is randomised, so swapping the arm labels within each (variant, round) pair, the same swap for every case sharing that execution, draws from the exact null distribution of the whole analysis (the seventh cold read of this draft, on the raw files):
- **Coverage is nominal:** the 95% t interval covers no change in 95.3% (a1) and 95.5% (a2) of swaps, averaged over 52 cases (lowest 92%), and in 94-95% for every window in c11 and c12.
- **c12 is a tail draw:** its windows' +3.8% to +5.7% sit at randomisation p 0.014-0.030; c11 and c12 differ by about 2.4 randomisation standard deviations (c12's own t standard error happened to be about 25% below its typical size, which made the gap look like 2.9).
- **The rate:** a null run of this window group shows at least one false *change* in about 6% of swaps (c11 and c12 alike). The correlation does not make the interval wrong; it makes the five windows' errors come together, so a run fails on all of them or none.
- **With §3.2's standardisation** (the mean of standardised log ratios) the coverage stays at 94-96% (in a null run even without its added error term), the randomisation standard deviation falls by 25-30% (c12: from 2.2% to 1.5%), and the chance of a false *change* per run falls to about 3-4%.

So the interval is calibrated, and the lottery is a large source of variance, shared by the cases in an execution, whose tail produces a false *change* in a few percent of runs. Two rates must be kept apart. The rate at which a calibrated 95% interval excludes 1 is about 5% per case in a null run however narrow the interval is (per run, at least one of msum100, mavg100 and mdev100 excludes 1 in 5.8-6.3% of swaps today and 6.3-7.3% standardised); narrowing the interval lowers only the false-*change* rate, because the 3% threshold starts to bite (from 6.0-6.7% to 3.6-4.0% per run on the five windows). Criterion (c) as written (both main-against-main runs with the windows' intervals containing 1) therefore fails about 12-14% of run pairs whatever the method, and up to about 27% of run pairs as the variance shrinks, since removing the shared lottery component de-correlates the windows (towards 1 − 0.95³ ≈ 14% per run).

### 2.6 placemat changes history and the environment between slots and batches

- **The case list.** Adaptive stopping drops cases from `PLACEMAT_CASES` between batches (c12's first batch timed six cases, its later ones five: s_mmin100 stopped after the first, removing it from between s_mdev100 and s_mavg10 in the script), so later cases in a later batch run after a different history, and `placemat check --affected` runs subsets whose history differs from a survey's. On these runs it did not matter measurably: at 0x300000000, where times repeat to about ±0.5 ms, pad 0 in batch 0 (s_mmin100 included) and the later anchors (s_mmin100 dropped) agree within 1-2% for the cases after the dropped one (s_mavg10 33.66 against 33.07 ms in c11, 32.77 against 33.14 in c12; s_mavg1000 37.11 against 36.77, 36.60 against 36.28), as closely as s_msum100, which runs before it. Dropping lines also changes the script's length (`bench.k_subset`) and `PLACEMAT_CASES` the environment's, which matter if the interpreter reads the script into the heap or the runtime copies its environment.
- **The bytes above the stack** (DESIGN §5.1's runner, `slot_env`): every execution gets `PLACEMAT_CASES` (which changes between batches), but the stock slot gets none of the data method's variables, of which the stock setting has six, the coloured setting seven and the stepped setting eight (`PLACEMAT_STEP_MODE` and a decimal seed of up to 20 digits); `PLACEMAT_LOG` holds a temporary path (of fixed length within a run), as does `DYLD_INSERT_LIBRARIES` or `LD_PRELOAD` under the interposer; and the binary's path includes the pad's tag (`p76-h` against `p3508-h`). Strings and their pointers are copied to the top of the stack at exec, so the initial stack pointer differs by about 290 bytes between the stock slot and the others, and by tens of bytes between settings and pads. That confounds the stock-build comparison (and with it DESIGN §5.7's "stock code layout" attribution, used by Amber's criterion (b)), the colour and step contrasts, and the code axis, with stack shifts of unknown effect.

## 3. Heap placement

### 3.1 Model

A case's data placement is set by the data setting (designed); the region bases (drawn per execution by the system); the heap's history when the case starts (fixed within a placemat run when the allocator and the program are deterministic, the program single-threaded and the cases before it constant; varying otherwise: a per-process hash seed, such as Lua's, varies it); and, for allocators that randomise large mappings separately (macOS's malloc for medium and large blocks), per-block draws as well. The execution is the unit that carries this variance: repetitions inside one execution share its placement, so they add almost nothing, and cases in one execution share its draws, so a chance imbalance moves a group of them together. *Change* verdicts have no multiplicity control (flags do), so such a group errs all or nothing.

### 3.2 Repair the run test and the estimate

1. **The run test by kind:** groups by kind (stock, coloured, stepped), the variants as strata within a kind, so no group is a single 7-execution variant (§2.2's floor); the anchors enter the stock kind; the max-|z| over the kinds is each arm's run p, combined over arms as today (the smallest times the number of arms) for BH; each kind's p and effect are reported. This is solid and should be done regardless, but it ships together with the removal of today's post-stratification path: with grouping by kind every lottery-heavy case is run-flagged, so today's trigger (run p < 0.05) would switch those cases to `strat_ratio`, which §3.7 rejects. The estimate is then the unstandardised median for every case, flagged or not, until item 6 chooses an estimator.
2. **Standardise whenever a covariate is available** (not only when the run test fires: a triggered estimator switches estimand between replicate runs near the trigger, as Amber's b1 and b2 would under item 1's grouping (run p of at least 0.028, under today's 0.05 trigger, though not significant after BH); when the covariate's effect is about 0 standardising changes nothing, as b1 and b2 show, moving at most 0.3 points with the same flags). Estimate the covariate's effect δ per (arm, kind), signed, from all of that kind's executions as a within-variant (stratified) estimate, as `stats._group_z` computes it, so code-layout differences between variants cannot bias it (the anchors in the stock kind), and standardise every execution: log y' = log y − δ̂·(I − s), with I = 1 at the pooled mode and s the mode's share pooled over both arms and all of the layout variants' executions (the base depends neither on the data setting nor on the pad (the slow-base share by pad is consistent with no dependence in all eight runs: χ² 4.7-12.8 on 11 degrees of freedom, b2 15.4 on 7), which the code test relies on too, and pooling keeps s's own error small; the run test's group estimate uses per-arm modes, so δ̂ is re-estimated against the pooled mode). The estimand is then named explicitly: the geometric mean at the natural mix of bases (not the median of a mixture), and each variant's location is the mean of its standardised log ratios, not their median, which the standardised spike makes overconfident (§2.2). For the mean, standardising changes only the variance, not the estimand: the adjustment −δ̂·(I − s) has expectation zero at the natural mix, so the plain and the standardised mean both estimate the geometric mean at the natural mix (c21: −51.6% and −50.8%), with or without a covariate. The median, a trimmed mean and Hodges-Lehmann's estimator do not have that property: under a multimodal lottery the per-variant median of 7 ratios jumps between modes when the slow base's share is near a half (c21's −54.1% against c22's −52.5% at the base arm's slow-base shares of 0.51 and 0.44 fits that). The mean's cost is heavy tails: on a noisy run it is less precise than the median (a2: randomisation standard deviation more than 20% worse on 24 of 52 cases, up to 2.5× on microbench-q's qij; a1 and b2 about 15% better). So the location estimator is chosen once, for every case and run, on four criteria: estimand invariance (to the covariate's availability and to the realised mix: the mean has it by construction, the robust estimators not under a multimodal lottery), and, by the arm swaps of item 6, coverage, randomisation standard deviation and false-change rate. A candidate to test is the mean with detector-flagged rounds dropped from both arms; whether a2's heavy tails come from whole-round disturbances (which largely cancel in back-to-back pairs) is untested. **Now** (items 1 and 2 ship together, so the tests are never adjusted by today's triggered `adj()` with kind keys): the verdict's estimate is the unstandardised median (calibrated: §2.2); the standardisation applies to the tests, the anchors' scaling and the disturbed-round detector; the standardised mean is reported beside the verdict as a diagnostic, without the error term below; the standardised median is not an option (82-87% coverage). **After item 6** chooses an estimator, the verdict uses it, and if it is a standardised one, the error term below enters its interval. The change interval adds, in quadrature to the t standard error over pads, the error of the standardisation that does not average out over pads: Var = Σ_K w_K²·[(s_main,K − s)²·SE(δ̂_main,K)² + (s_base,K − s)²·SE(δ̂_base,K)²] + (Σ_K w_K·(δ̂_main,K − δ̂_base,K))²·SE(ŝ)², where w_K is the per-pad weight of kind K (1/3 when both offsets vary, 1/2 when one does, 1 with the data axis skipped) and s_a,K the share among arm a's layout variants of kind K (anchors excluded): 0.10-0.19% on c11 and c12, 0.34-0.55% on c21 and c22, the last term's expectation being 0 in a null run. This answers DESIGN §5.7's warning that a pooled adjustment once spread its error across variants and made false −5% changes: here the shared error is carried in the interval. It is approximate (δ̂ and the per-pad means share data), which item 6's resampling check covers. The code, colour and step tests, the anchors' scaling and the disturbed-round detector run on the standardised times (and the estimate too, once item 6 has chosen an estimator that is calibrated on them). Contrast-only slots (the isolation slot, §3.6; the stack slots, §4.3) run under another history or environment, so each gets its own δ̂ per arm, or is left unstandardised and says so; they are never pooled into the stock kind. For an arm-specific covariate (the k hash) each arm is standardised to its own share, which reduces variance but cannot correct a chance imbalance. Report the unstandardised result beside the standardised one, and the estimand's move.
3. **What standardisation does and cannot do:** it removes the slow mode's share of the variance (§2.5: the false-change rate per run from about 6% to 3-4%), not the other bases' (§2.2): on c12, s_mavg10 sits at the threshold (+3.04%, or +2.99% with the anchors left out of δ̂). (That four of its windows' intervals still exclude 1 is not a defect: a calibrated interval does so in about 5% of null runs per case, §2.5.) Beyond it, two repairs reduce the variance further: **more rounds** for run-flagged cases, by Kalibera & Jones's dimensioning with its costs (DESIGN §5.1, planned): pads would add independent executions too, and degrees of freedom, but the windows are at the 12-pad cap and each pad costs builds, so rounds are the cheaper lever here: quadrupling c12's rounds would add about 7 minutes of timing and cut the standard error by up to half (fully only when the within-pad variance dominates, as in a null run); and, for hook projects, **pairing** both arms of a pair on one base (§3.3), which cancels every base's effect rather than shrinking it, and also pairs the within-pad contrasts. With any of them a correct method still produces a false *change* now and then; how criterion (c) treats that is the user's decision (§3.7).
4. **Safeguard against a real change in the covariate:** report each arm's category shares per kind, and Fisher's exact test of arm × category, and always both estimates, the one at the common natural mix and the one at each arm's own mix (per-base effects reweighted by the arm's shares; as §3.3 does under hints); a real change can move the base distribution (a larger binary, other mappings), and Fisher's test only adds a warning, never switches the estimate the verdict uses (switching on a test with about 60% power for a 10-point shift at 252 executions per arm would be a trigger again).
5. **The disturbed-round detector** runs on standardised times, and ignores the slots that have no covariate (the stock slot) for run-flagged cases, so a lottery is not read as a slow machine.
6. **Validate by arm swaps** (no timing): on every null run whose arms share binaries (Amber a1, a2, c11, c12 today), swap the arm labels within each (variant, round) pair, the same swap for every case in that execution, and recompute everything (ŝ, δ̂, the interval) per swap: coverage, randomisation standard deviation and false-change rate per case and per run, for each candidate estimator (item 2); this also tests the error formula. Then on real changes (c21, c22, b1, b2): changes and flags kept, the estimand's move reported; on every null run: no new code flags, new run and colour flags listed and each checked against its natural-mix effect (c11 and c12 are expected to gain them), the code test against the rank test. The swap is exact given the realised pad counts; adaptive stopping on width depends on the labels, which matters for cases that stopped early (a1's and a2's 4-pad cases), not for the windows at the 12-pad cap. Arm swaps become a command (`placemat reanalyse --swaps N`, refused unless the arms share a tree), so a null run reports its own operating characteristics. Candidate estimators are judged by these rates, not by what they do to c12, which is one tail draw.

### 3.3 Pair the lottery where the method can

The hook can ask the project's allocator to map its first large region at a hint (`PLACEMAT_REGION_HINT`), the same for both arms and for every slot of a pad in a round (per round and pad: its three variants, and its isolation and stack slots), recorded, so a pair's executions share their base and every base's effect cancels in the paired ratio, not only the mode's (§3.2 item 3): for hook projects this is expected to be the strongest repair of §2.1's problem, though untested where it matters most: low-range hints overlap where other executions' images and early mappings sit, so they will be refused most often in the population that carries the variance (§2.1); every hint result (refusal rate, paired spread) is reported per population, with the slide and the stack (`argv`) address logged beside the base. Hinting per (round, pad) also pairs the within-pad contrasts on base (the colour and step sign-flip tests, the isolation and stack contrasts), which would otherwise compare executions at independent bases; pads stay independent units for the t interval. Only the code test (pads compared within a round) and the anchors still see the lottery and use §3.2's standardisation. (One hint per round for every pad would also pair the code test, but it correlates the pads, so the t interval would need care; not proposed.)
- **Which hints:** drawn from the bases this machine's allocator produces unhinted, from a calibration (an unhinted run of the project's own build, kept per machine), so the mix stays the natural one and a hinted (0, off) remains "the stock placement" for DESIGN §5.7's attribution; uniform hints would change the estimand (they would almost never draw 0x300000000, which half the executions get naturally). Whether the base matters as an absolute address or relative to the program's image is open: executions at 0x300000000 repeat to about ±0.5 ms across executions with different slides, which favours absolute, while a natural low base sits in the first gap after existing mappings, so an absolute low base copied into an execution with another slide may give a combination of base and neighbours that never occurs naturally. So the data method logs the main image's address (the slide) with the base, hints are absolute, and validation checks that hinted executions at base b reproduce the natural time at b (else hints are given relative to the slide). Hinting both arms alike also hides any real effect a change has on where its region lands (a larger binary or other mappings change which gap the region fits), so the unhinted sample comes from the discarded execution of each binary and data setting that DESIGN §5.1 already runs before every batch (whose bases the runner must then record in the raw file; today it discards them) (36 per arm per batch in a survey, at no extra timing), whose bases give the per-arm shares and can supply this run's own hint distribution beside the per-machine calibration; but at 36 per arm Fisher's test has about 14% power for a 10-point shift (against about 60% at 252), so some timed rounds stay unhinted (a whole number per batch, two of seven say, sized for the power wanted). They do not enter the paired estimate, which uses the hinted rounds only (5 hinted rounds at a paired standard deviation of about 0.03 plus 2 unhinted at about 0.3 would give about 0.06 per variant against 0.011 with all 7 hinted; 0.03 is the figure at 0x300000000, and low-range bases repeat only within 3-7%, so hinted pairs there will be noisier); the unhinted rounds and the warm-ups feed the shares and s, Fisher's test and the arm-specific estimate. The hinted estimand is named in the report: the effect at a common natural mix of bases, conditional on the calibration's mix (a finite calibration adds sampling error, the analogue of SE(ŝ) in §3.2 item 2: about 0.5 points on a c21-like change, none in a null run; either add it to the interval or state the condition) (a mean-type estimand; with a median it becomes the median over bases, §3.2 item 2). Where a real change may move its region (a larger binary, other mappings), an arm-specific alternative is reported beside it: the per-base paired effects reweighted by each arm's own unhinted shares. Under hinting, s in §3.2 is the share among those unhinted executions (or the calibration's), not among the hinted ones, which are the design's own draw and biased by refusals.
- **How:** only the first anonymous region (Amber maps large regions of its own); macOS: `mach_vm_allocate` with `VM_FLAGS_FIXED`, which fails safely if the range is taken (a plain `mmap` hint is honoured only when free); Linux: `MAP_FIXED_NOREPLACE`, never `MAP_FIXED`. A refused hint falls back to the natural base, which the log records; a pair whose arms ended at different bases is analysed by its logged bases as now. Refusals are not random: the natural low bases sit in the first gap after existing mappings, whose position moves with each execution's slide, so low hints are refused more often, biasing the realised mix toward 0x300000000 and losing pairing selectively; the refusal rate per hint is reported. On Linux before 4.17 `MAP_FIXED_NOREPLACE` is ignored, so the returned address is always checked.
- **Limits:** only the hook can do this (the colouring allocator and the interposer get their blocks from the system allocator), and the stock slot, which has no hook, keeps its lottery (§2.3; a preloaded shim hinting `mmap` could pair it, at the cost of its no longer being the stock build): for a run-flagged case without a covariate in the stock slot, the stock-builds result and the "stock code layout" attribution are reported with the number of rounds they would need (computed per case from the stock pair's variance; §2.3), not as noise; on Linux the runner could read the stock slot's base from `/proc/<pid>/maps` as a covariate.

### 3.4 Keep the history the same within a run

A cheap precaution, since §2.6 found no measurable effect of a dropped case on the cases after it: keep the cases that precede any still-running case in the list (a case's history depends on the cases before it, and on the script's and environment's lengths if they reach the heap), timing them and discarding their results, so every batch, the anchor and `check --affected` run each case after the same predecessors; cases after the last running case can be dropped as now. `[[suite]] keep_prefix = true` (which matters only in multi-batch runs: a survey is one batch and drops no cases) is the default for suites whose cases share an execution (K `out[]` scripts and name/value harnesses; not hyperfine, where each case is its own process). Cost: in `run` and `survey`, the predecessors' run time in later batches (on Amber small against lock waits); in `check --affected`, keeping every predecessor of the last affected case would run most of a 200-case script and undo DESIGN §3.3's saving (200 cases to 10-30), so `check` keeps no prefix by default and its report says that its history differs from the survey's. With case order varied (§3.6), the prefix is taken in the round's order. Where cases are dropped (after the last running case, or in `check`), `bench.k_subset` replaces their lines with comments of the same length, so the script's size does not change.

### 3.5 The fingerprint

- **What:** per execution, the full addresses of the large blocks (at or above the colouring threshold) with their sizes and their offsets within their regions, plus the region bases; per case, the blocks allocated during it and the blocks live at its start. Full addresses, because §2.1's mechanism sits above the page: the analysis looks for the address bits and the distances between mappings that separate slow executions from fast ones, the data analogue of the code culprits (DESIGN §5.6). The binary "most common base or not" category stays the run test's covariate; the fingerprint is for explanation.
- **Case marks:** the harness calls `placemat_mark(index)` before each case: a C call in harnesses that can make one, or a primitive the project's adapter adds for script harnesses (an Amber K primitive in hooked builds). Every data method provides it and writes the mark into its block log, in order with the blocks, so no second clock is needed; in the harness it is a weak reference with a null check (or looked up with `dlsym`), so a preloaded interposer can provide it and a build without a data method skips it. The stock slot has no data method and so no marks, and its build cannot contain the mark primitive, so in its script the mark calls are replaced by comments of the same length (as §3.4 does for dropped cases), keeping the script's size and order. Encoding marks as allocations of a magic size does not work: the hook logs only blocks at or above the threshold, recognising a smaller sentinel would put a check on the small-block fast path (DESIGN §7 forbids it: such a check cost 3-10%), a size-class allocator has no unused sizes, and the sentinel's first use of a class can split a free block and change the history it observes. Whether marks perturb timing is checked by a null run with and without them, comparing the stock pair as well (a mark primitive that allocates is one more difference between the stock slot and (0, off)).
- **What it needs:** the block log (`PLACEMAT_ADDRLOG=2`) kept for every execution instead of discarded once read (the runner uses level 1 and discards logs today), with its 4,096-event cap replaced by a per-case limit (c12 logged about 70 coloured blocks per execution, well under it; allocation-heavy cases would not be).

### 3.6 History as a factor (surveys and audits)

- **Isolation contrast.** `[[suite]] isolation = "script"` (default: one execution per suite, as now) or `"case"` (one execution per case, after the suite's set-up). `placemat survey --isolation` adds one slot per pad, its stock setting under case isolation, and the contrast script/isolated is tested and flagged like colour and step (family *isolation*). The isolation slot is a contrast-only slot like the stock slot: not a layout variant, so it does not enter the per-pad geometric mean, the code test, batch counting or the data-dependence split (DESIGN §5.7's two-thirds weighting of the offset settings is unchanged). It is not a pure history contrast: an isolated case also starts with cold instruction caches and predictors and fresh page mappings (first-touch faults), so an isolation flag says "depends on running after the others" and the fingerprint says whether placement is why. Cost: per pad, per arm and per round, one execution per case, each repeating the suite's set-up: for a 200-case suite at 12 pads and 7 rounds, 16,800 isolated executions per arm (33,600 for both), roughly an hour of set-up alone at about 0.1 s of set-up per execution; a survey would time it on a subset of cases.
- **Case order** as a random factor: placemat draws one order per (round, pad), shared by that pad's slots and both arms, with a recorded seed, so a pair and the pad's within-pad contrasts share their history, the pads draw their orders independently (so the t interval over pads carries the variance of drawing orders, as §3.3 keeps pads independent for hints), and the result averages over orders; the code test, which compares pads within a round, is left unpaired on order, the same trade-off §3.3 accepts. The stock slot takes pad 0's order in its round; the anchors of later batches see other orders than pad 0 did in the first batch and average over orders as the pads do. Reordering makes the k hash stop repeating (the region-base covariate survives, though its effect can then depend on the order), and it does not stop a group from moving together (cases in one execution share its draws). Off by default; a suite allows it with `[[suite]] reorderable = true`, and for `k-out` scripts placemat can reorder the `out[]` lines itself (`bench.k_subset` keeps every other line in place), safe only when all set-up precedes the first case.
- **In-place repetitions** (DESIGN §2's iterations) stay the harness's business; placemat should not add them for precision on placement-sensitive cases (they repeat the placement), and may report their spread within an execution against the spread between executions as a diagnostic.

### 3.7 Considered, and one option for the user

- *Confirming a history-sensitive case's change at the stepped setting:* the stepped setting gives both arms the same designed relative offsets only when they allocate identically (a null run), it changes those cases' estimand from DESIGN §5.7's average over three settings to one setting's sign, and a change acting only through the shipped placement would be relabelled *placement*.
- *Tightening the change rule for every case* (p ≤ 0.01 and FDR): costs power everywhere and still lets a correlated group pass together.
- *An "unresolved" verdict for every case whose interval excludes 1 but whose nearer bound lies inside the threshold:* across all of placemat-work's reports it would relabel 19 of 87 *change* verdicts, including real changes of 3-5% that replicate (the page-cache check-in's ipk_lookup, −3.1% on the Mac and −3.3% in the VM; Amber's setdictnest and setlistdictall in both b runs); defining it by the interval's width instead would relabel the prototype windows' −52% to −67% changes. **A narrow version is the open option for the user** (with §3.2 item 3): *unresolved* only for run-flagged cases (whose errors are correlated within a run) that are not paired by a hint, when the nearer bound lies inside the threshold. With the run test grouped by kind, Amber's b1 and b2 are not run-flagged (run p at least 0.028, not significant after BH), so the option leaves setdictnest and setlistdictall alone; SQLite's ipk_lookup is to be checked in §3.2 item 6. In the verdict order *unresolved* replaces only *change*, is decided before *placement*, and keeps the flags as qualifiers; since grouping by kind makes every lottery-heavy window run-flagged, such a case is otherwise *placement*. Under the standardised mean it would turn c12's s_mavg10 into *unresolved* rather than *change* (under the interim median all five windows' nearer bounds lie inside 3%, so all five would be *unresolved*); either way it does not meet criterion (c) as written, since c12's windows would still have intervals excluding 1.
- **The options for criterion (c), for the user:** (i) restate (c)'s main-against-main half as "no *change* verdicts" (parallel to the restatement offered for (a)), with the false-*change* rate measured by arm swaps stated beside it (§2.5: a run pair fails about 12% of the time today and with the interim median, about 7% if the standardised mean is chosen, and less again with more rounds or hints, untested); (ii) keep (c) as written and accept that it fails about 12-14% of run pairs whatever the method (more as the variance shrinks, §2.5); (iii) if an interval-based criterion is wanted, a family-wise interval over the window group (adjusted for the three or five windows) in place of per-case intervals: it fails at most about 5% of null runs and 10% of run pairs whatever the precision (Bonferroni being conservative for correlated windows, slightly more often as precision de-correlates them). (iv) judge the method rather than one draw: (c)'s main-against-main half passes when, in both runs, the arm-swap coverage is at least about 93% and the per-run false-*change* rate at most a stated bound (5%, say, estimated from 10,000 swaps so that its own Monte Carlo error is small against the bound; today's estimator gives 6.0-6.7% per run on the five windows, so at 5% (iv) passes c11 and c12 only with the standardised mean, 3.6-4.0%), the realised verdicts being reported, not gated on (needs `reanalyse --swaps`, §3.2 item 6). More rounds and hints (§3.2 item 3) help only under (i) or (iv).
- *Per-variant post-stratification* (today's `stats.strat_ratio`), whether triggered or always on: unpaired, weighted by the smaller count, and skipping or mishandling sparse cells (§2.2); replaced by §3.2 item 2's standardisation.

## 4. Stack placement

### 4.1 Measure first

At exec the kernel copies the argument and environment strings (and on macOS the `apple[]` strings, among them the executable's path and inode and several random values printed in hexadecimal) to the top of the new stack, places the pointer arrays below them and aligns the stack pointer to 16 bytes; it may also randomise the pointer: Linux's `arch_align_stack` subtracts a random amount below 8 KB on x86-64 and, to be confirmed, below a page on arm64, so under Linux address randomisation the offset mod 4 KB is uniform per execution and an environment-driven axis would be moot there; macOS is to be measured. How much of the initial stack pointer's offset is randomised, at what granularity, and how much is set by the block above it, decides the design, so it is measured first: a small C program reporting `argv`'s address (set by the block itself, unlike a local's address in a constructor, whose depth varies with the loader) and a local's address in `main` (what the program's frames see, in case the loader's frames before `main` depend on the strings) mod 64 B, 4 KB and 16 KB, over 100 executions per environment size, for sizes 0-64 bytes in 1-byte steps and a coarse grid to 16 KB; on macOS arm64 and in the Linux VM (and on x86 when available). The result is a distribution of jitter per size, not a yes or no.

The mechanisms by which the stack's position changes speed: the alignment of stack arrays and spill slots against cache lines; their L1 sets against hot heap buffers; on Intel x86, loads falsely depending on earlier stores 4 KB apart, which a stack spill and a heap array can hit. The colour setting already moves large heap blocks relative to the stack (DESIGN §5.3), so what only a stack factor varies is the stack against code, static data and small heap blocks.

### 4.2 Hold what placemat controls

Whatever the measurement shows, placemat should stop moving the stack by accident (§2.6):
- `PLACEMAT_STACK_PAD`, set per execution to the target size minus everything else above the stack (strings and their pointers, 8 bytes each), makes the block placemat controls a constant per machine: it absorbs differences in variable names, values and path lengths by itself (up to 16 KB of padding in every slot, the stock slot included, so the stock slot's stack is no longer exactly the shipped one; reports say so). Holding the parts constant as well (the same `PLACEMAT_*` names in every slot, with a dummy of the same length where other slots preload the interposer; fixed-length binary and temporary paths, at the price of a one-time cache rebuild) is optional belt and braces; zero-padded numeric values are safe for `placemat.h`'s parser, but a project hook that reads them with `strtoul(…, 0)` would take them as octal, so placemat does not pad values;
- everything the runner passes counts: `PLACEMAT_CASES` (it changes when cases are dropped; the stack pad absorbs that, without changing the benchmark protocol's format), `PLACEMAT_SERIES`, the script path in `argv`, and the inherited variables (`inherit_env = false` is the default: PATH, HOME, TMPDIR and LANG only); on a `[target]`, children start under `env -i` with the same block, since the ssh layer adds variables of varying length (`SSH_CLIENT`, `SSH_CONNECTION` carry ports).
- What placemat cannot hold: macOS's `apple[]` strings vary per execution (random values) and per binary (the inode), so on macOS the goal is the same distribution in every slot, not the same address. The data methods' constructors log `argv`'s address as a check (§4.3); the stock slot has no data method, so a harness that can print `argv`'s address (or the hook's start-up in hooked builds) is the check there.

### 4.3 Record, then vary if worthwhile

- **The covariate.** The initial stack offset (from `argv`'s address) mod the L1 set stride, logged per execution and reported (its distribution per slot, and the run test's z for it in coarse classes), but not used to adjust: a randomised offset does not repeat, and its effect, if any, is expected to be cliff-shaped (an array crossing a line or sharing a set) rather than smooth in the offset, so neither a category nor a linear standardisation (§3.2) fits it; a joint scheme with the region base is open.
- **The axis, if the offset is not randomised within a page:** the length of `PLACEMAT_STACK_PAD` moves the stack pointer in 16-byte steps, with no build change. A stack setting is a slot-level factor like colour: each pad's stack slot runs its stock setting at offset o_j for all its rounds and for both arms, where o_j = 16·⌊(span_s/16)·frac(w₃ + j·√7)⌋ over one L1 set stride, with w₃ recorded and drawn from the run seed after w₁ (so seed 0 still reproduces Amber's pads and steps), and every other slot runs at the reference length. √7, not √5: √5 = 1 + 2/φ, so frac(j·√5) = frac(2j/φ) would tie the offsets to the pads' generator. The block's constant size (§4.2) is the reference plus the largest o_j, so every offset is reachable by shortening the pad.
- **The contrast:** the stack slots against the stock setting, flagged as family *stack* (qualifier *stack-dependent*) by the test below rather than colour's and step's sign-flip test. Stack slots are contrast-only slots like the stock slot: not layout variants (DESIGN §5.7's per-pad mean, code test, batch counting and dependence split are unchanged). A contrast against one reference can flag the reference rather than the program (as Lua's `tbl_array` colour flag described the colouring wrapper's own (0, off), DESIGN §7), so the stack family flags on heterogeneity across the o_j: the statistic is the spread of the per-pad stack contrasts, its null distribution from permuting those contrasts among the pads within a round (assuming pads exchangeable within a round, as the code test does; it also picks up an interaction of code layout and stack), and the mean contrast against the reference is reported separately.
- **If the offset is randomised within a page,** the stack is already a random run factor: the covariate is the tool, and an axis adds little. Turning randomisation off (Linux: the `ADDR_NO_RANDOMIZE` personality, `setarch -R`; macOS: the private `posix_spawn` flag that LLDB uses) freezes the stack and the heap regions at once: one placement for the whole run, good or bad, which suits pairing, not estimation.
- **A start-up shim** (a constructor or `main` wrapper that allocates a designed amount of stack before calling the program) would give finer control than the environment but needs a build change in every arm and moves code; it is the fallback if the environment cannot reach the offsets needed.
- **Side effects:** a program that copies its environment to the heap gets a different heap history from a longer pad (at most one span, 16 KB); check whether the project does (Amber's K runtime first).
- **Threads** (DESIGN §5.8): other threads' stacks are placed by the thread library; this covers the main thread only.
- **Fixes**, if a project turns out stack-sensitive, are the project's: realign or pad the sensitive frames (an `alloca` in `main`, `-mstackrealign`, aligned arrays).

### 4.4 Validation

(1) The measurement of §4.1. (2) A weak check on old runs: do colour and step flags line up with the setting's block size? (The stock slot against (0, off) differs in the hook's code, the pad, the environment and the lottery at once, so old runs cannot isolate the stack; null runs cannot show it through the stock pair, since both arms share their environment.) (3) With §4.2 in place, a null run with the stack covariate (or `--stack`, if not randomised) on Lua, SQLite and Amber; any stack flag is a new finding.
