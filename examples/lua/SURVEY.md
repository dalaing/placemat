# placemat survey: Lua 5.4 on Apple M2

P010 (planning/ISSUES.md), DESIGN §3.1: does Lua's interpreter have a placement problem on this machine?

## Verdict

> **Gating.** The conclusions use the gated runs: `null-547`, `rel-546-547` and `rel-546-547-b`, timed with placemat's noise gate (`[machine] max_noise = 0.05`, `wait = 2700`). One batch of `rel-546-547` went ahead after the full wait at a probe spread of 6.1%. The first versions of those three runs were timed before the gate existed (worst probe spreads 12.6%, 5.2%, 9.0%) and are kept as `*-ungated`; they are quoted only where they agree or to show what noise did. The code-only runs `code16-547` (worst spread 0.9%) and `a16-547` (4.2%) were single-batch, quiet and ungated, and stand as they are.

**Lua 5.4 on Apple M2 has a code-placement problem of 2-12% per case, with no data-placement problem in the stock build.** The gated null run (5.4.7 against itself; both arms are the same binaries, so each arm is an independent replication) code-flags 5 of 18 cases in *both* arms (`fib`, `loop_int`, `loop_float`, `array_stream`, `nbody`; `tbl_sort` in one), with code spreads of 3-12%. The largest single cause is the 8-byte phase of the interpreter's code, not 4 KB boundary crossings. Every 4-byte pad step moves all of Lua's 4-byte-aligned code, and the speed of `fib`, `loop_int` and `array_stream` depends on luaV_execute's address mod 8, by 2-5% with case-specific signs. That is replicated in four runs (the code-only run, the gated and ungated null runs, and the default arm of `a16-547`). The ungated null run had flagged nothing: the machine was too noisy and the adaptive design stopped at 4-6 pads. Per DESIGN §3.1 the verdict is *code spread*: pinning would help, and the simplest pin works. With `-falign-functions=16` every pad leaves luaV_execute ≡ 0 mod 16, and fib's phase contrast falls from +4.4% (default build, same run) to +0.4%; the aligned build's layout-averaged speed is within ±1.2% of the default for every case (`a16-547`). The spread is as large as the real 5.4.6 → 5.4.7 differences (±1-3%), so a plain A/B of two builds can get those differences wrong, sign included.

- **Null run, gated (`null-547`; 5.4.7 against itself, data both, adaptive, noise gate 5%):** no *change* verdicts; 17 of 18 intervals contain no change, all within about ±1.5%. Code flags, per arm (p ≤ 0.01): `fib` 3.4% / 4.4%, `loop_int` 5.9% / 5.1%, `loop_float` 3.2% / 3.6%, `array_stream` 4.9% / 3.8%, `nbody` 11.7% / 10.0%, `tbl_sort` 5.4% (one arm). `placemat culprits` (now with an address-phase check) reports alignment for each: slow and fast pads split by the code shift mod 16, 32 or 64, with no candidate 4 KB loops. `tbl_array` is again flagged for colour and step (the wrapper's (0, off), below). The stock-build pair came out *measurable* for 4 cases although both stock builds are the same binary: `str_pattern` +4.7% (+0.8..+5.2), `tbl_array` −5.7%, `tbl_hash` +3.7%, `closures` −3.0%. The 7-round percentile bootstrap of the stock pair is overconfident (issue 9 below). Batch 0 started at load 4.2 and ran about 35% slower than every later batch in every case (`loop_float` 140.7 against 104.2 ms). The noise probe passed (spread 1.2-3.3%) because it measures spread, not level (issue 10). Paired ratios, the within-batch code test and the anchor-rescaled spreads are unaffected. 6.5 h wall clock for 11 minutes of timing.
- **Null run, ungated (`null-547-ungated`):** the same verdicts on changes, but no code flags (4-6 pads per case, worst probe spread 12.6%).
- **5.4.6 → 5.4.7, gated, two runs (`rel-546-547`, daytime, one batch went ahead at probe spread 6.1%; `rel-546-547-b`, overnight, quiet; data both, adaptive, 4 → 12 pads):** no *change* verdicts. Small real differences, under the 3% threshold and the same in both gated runs and both ungated ones: `fib` +1.2% (+0.4..+2.1) / +1.4% (+0.4..+2.4) [ungated +1.3%, +2.4%], `tbl_array` +1.7% / +1.3% [+1.7%, +3.2%], `tbl_sort` −2.4% (−3.1..−1.7) / −2.4% (−3.2..−1.7) [−2.3%, −1.3%], `json` +1.0% / +1.1%, `closures` +1.1% / +0.9%. Code flags on 6 and 7 cases (`fib`, `loop_int`, `loop_float`, `str_pattern`, `array_stream` in both runs); placemat's new rank-based test agrees.
  **Measurement bias, replicated three times.** The stock builds' own paired result disagrees reproducibly with the layout-averaged one:

  A plain A/B of the two release builds says 5.4.7 is 2-3% faster at recursive calls (`fib`) and 2-3.5% slower at integer loops; layout-averaged, calls got 1.3% *slower* and integer loops did not change. The stock pair's interval alone is not trustworthy (issue 9: the null run produced 3-6% "measurable" stock differences between identical binaries), but these four repeat in sign and size over three runs, while the null run's do not. So the stock layouts of 5.4.6 and 5.4.7 really differ in speed for reasons unrelated to the change. placemat's "if placement were ignored" summary: a single-layout comparison could have reported a false change in 11 and 10 of 18 cases (one layout could show −4.2..+7.9% for `sieve`, −5.5..+6.1% for `array_stream`). Wall clock 6.8 h and 0.8 h; about 12 minutes of timing each.

- **Code-only follow-up (5.4.7 against itself, no data axis, 16 pads in one batch):** no code flags (per-arm p 0.03-0.8), but the per-pad medians split cleanly by luaV_execute's address mod 8 (ms: base arm, code-only run; effect: phase-0 pads' median over phase-4 pads'):

| case | luaV_execute ≡ 0 mod 8 | ≡ 4 mod 8 | effect of phase 0 (code-only, base / new) | same, ungated null run (hooked builds) | same, gated null run (hooked builds) |
|---|---|---|---|---|---|

| `loop_int` | 102.2 ms | 105.0 ms | −2.8% / −1.6% | −4.3% / −5.0% | −3.6% / −2.6% |
| `array_stream` | 96.4 ms | 98.7 ms | −1.8% / −2.8% | −3.4% / −3.3% | −1.8% / −3.4% |
| `spectral` | 145.4 ms | 143.7 ms | +0.9% / +2.1% | −1.8% / −0.0% | −0.1% / +0.4% (sign not consistent) |
| `loop_float`, `methods`, `closures`, `nbody` | | | under 1.5%, no consistent sign | | `nbody`, `loop_float`: code-flagged, not by the mod-8 phase (culprits: slow pads separate by code shift mod 16 for `loop_float`, mod 64 for `nbody`) |

  Within each phase class the medians are tight across the whole 4 KB period: fib's eight phase-4 pads all fall within 74.3-74.9 ms. So there is no 4 KB crossing effect on top of the phase. Every 4-byte pad step moves all of Lua's code, because the objects are only 4-byte aligned. The design's pads alternate between the two phases (P_j mod 8 = 4 for even j and 0 for odd j, with seed 0's v = 13), so the effect sat in plain sight in the pad order. The sign depends on the case's opcode mix, which fits fetch alignment of the computed-goto handlers in luaV_execute (13.5 KB, one function). The stock 5.4.6 and 5.4.7 builds both have luaV_execute ≡ 12 mod 16 (phase 4).

- **Aligned functions (`a16-547`: 5.4.7 against 5.4.7 compiled with `-falign-functions=16`, via a `placemat-cflags` file in the arm's tree; no data axis, 16 pads):** in the default arm fib's odd-j/even-j (phase 0 / phase 4) contrast is +4.4% again (third replication; pads 4 and 13 left out as machine-disturbed), and in the aligned arm, where luaV_execute is ≡ 0 mod 16 in every pad, it is +0.4%. The other cases' phase contrasts were within ±1% in this noisier run in both arms, so for them the run is inconclusive. Layout-averaged, the aligned build is −1.1% (−2.4..+0.3) on `loop_int`, −1.2% (−2.4..−0.1) on `array_stream` and within ±0.7% elsewhere. Its stock build against the default stock build is +3.2% on `fib` and +5.8% on `closures` (*placement* verdicts: the two stock layouts, not the flag).

### Why the ungated survey missed it, and the culprit search

The gated null run found it with placemat's own tests. The points below are why the ungated runs did not; they still matter on any machine whose noise is heavy-tailed.


- **The code test lacks power under heavy-tailed noise.** It permutes pad labels within rounds and uses the sum of squares of per-pad trimmed means (dropping one minimum and one maximum of 7). On this machine whole rounds are sometimes disturbed: some executions run 20-40% slow, and the p90/p10 of run-to-run times was 1.15-1.3 in the null run. One trimmed outlier per pad is not enough. A Friedman-type statistic (rank the pads within each round; sum of squared rank-sum deviations; permute within rounds) on the same code-only data gives p = 0.0000 / 0.0004 for `fib`, 0.0088 / 0.0005 for `loop_int` and 0.0096 / 0.10 for `array_stream` (base / new). placemat's own test gave 0.06 / 0.03, 0.47 / 0.13 and 0.45 / 0.21.
- **Adaptive stopping stops early in a null run.** With identical arms the change interval is narrow at once, so most cases stop at 4 pads. With the noise above, 4 pads give the code test almost no power. A survey's null run needs a fixed, generous pad count (the 16-pad code-only run) to measure the code spread.
- **`culprits` looked only at small backward-branch loops crossing 4 KB** (it now also reports the address phase that separates slow from fast pads, which names the alignment cause for every flagged Lua case in the gated null run). Lua 5.4's hot cycle is handler → computed goto → handler: indirect branches inside one 13.5 KB function, with no small backward branch. For `fib` it correctly picked the five slow pads, all of them phase 0, but found "0 candidate loops". For `loop_int` it picked one slow pad and offered 19 loops in cold functions (`atomic`, `f_setvbuf`, `luaL_checkoption`, …) and 8 targeted pads: false leads without a hot-function list (`--hot`, which needs a profile). Grouping slow and fast pads by the hot functions' address mod 8/16/32/64 would have found this at once. That is a cheap test for `culprits` to add.

### Data axis

- **No data effect in the stock build.** Across both axes the colour and step contrasts are within noise for every case except `tbl_array`, including `array_stream` (three 1 MB arrays used together) and `sieve` (8 MB). Wrapped offsets: 0 in all runs.
- **`tbl_array`: an artefact of the wrapper's (0, off).** It is flagged for colour and step in all three data runs (p 0.0001; typical −10 to −12%), meaning it runs about 11% faster at any designed colour or step than at (0, off). The true stock build (≈39.7 ms) runs like the coloured and stepped settings (≈38-40 ms); only (0, off) is slow (≈44 ms). Every setting takes the same path in `placemat_alloc` (over-allocate, header, and on large-to-large `realloc` the underlying `realloc` and then a `memmove` to the payload's offset), so the only difference is where the payload sits: 64 B past the start of the page-aligned underlying block at (0, off), at the block start in the stock build (macOS returns large blocks page-aligned), and 64 + c at a colour. So `tbl_array` (a single array grown to 2 MB by `realloc`, then scanned) has a narrow bad window at "page + 64" that stock Lua does not hit. It is unexplained. The flag is correct about the hooked build, but placemat's report gives no hint that the stock build matches the offset settings and not (0, off).

### Run-to-run and machine noise

- The run covariate (khash) never flagged. Run-to-run spread is machine noise: in the null run and the code-only run both arms (identical binaries) show the same slow rounds.
- The machine was not quiet. quiet.py waits for load < 3 only when it takes the lock, and another session's unlocked LTO build loop pushed the load to 4-5.6 during release run 2. In release run 1, rounds 4-7 of batch 0 were 20-40% slow across the board (`tbl_hash` 29 → 90 ms), mid-batch. placemat's noise probe at the start and end of each batch missed it. Within-round pairing kept the change intervals valid (both arms slowed together), but the per-pad medians mixed disturbed and undisturbed rounds. That gave code spreads of 13-34% and three false code flags in run 1 (`fib`, `loop_int`, `array_stream`, each flagged in one arm only).

## Performance commits in Lua's history: a shortlist

Sources: the `lua/lua` GitHub mirror's log (5,861 commits; searched since 2019 for optimisation, speed, inline, table, string, GC and VM changes) and the lua-l archive. Lua's commit messages almost never cite a measurement: none of the ~20 commits titled "optimization" or "faster" gives a number. So every claimed gain below rests on reasoning about the code, which is where placement can mislead. The interpreter is placement-sensitive (above), and `ltable.c`, `lstring.c`, `ldo.c` and every file before `lvm.c` in link order move `luaV_execute` when they change size.

| commit | what it claims | why it is a placement candidate | cases that exercise it |
|---|---|---|---|
| [`2ff34717`](https://github.com/lua/lua/commit/2ff34717227b8046b0fdcb96206f11f5e888664e) "Using 'inline' in some functions" (2021-09-15; in 5.4.4) | Speed by ISO C's rationale ("calls to the function be as fast as possible"); no measurement. Marks number comparisons in `lvm.c` (`LTnum`, `LEnum`, `LTintfloat`, …), the call/return helpers in `ldo.c` (`moveresults`, `prepCallInfo`, `ccall`) and five `lapi.c` helpers (`index2stack`, `reverse`, `touserdata`, `auxgetstr`, `finishrawget`) `inline`. | It inlines code into `luaV_execute` and `luaD_precall`, which grows and reshapes the interpreter loop and moves everything after `ldo.o`. The expected gain is small (one call per comparison or return), the size of the measured placement spread. | `fib`, `closures`, `methods`, `vararg` (calls and returns); `loop_float`, `tbl_sort` (float and comparator `<`) |
| [`b34a97a4`](https://github.com/lua/lua/commit/b34a97a4af5c9e973915c07dba918d95009e0acd) "Small optimization in 'luaH_psetint'" (2024-01-25; 5.5 development) | Writes to existing empty array cells skip the slow path when the table has no `__newindex` ("quite common"); no measurement. A 5-line change to `ltable.c` and `ltm.h`. | A one-branch saving on the array-store path, while `ltable.o` is linked before `lvm.o`, so any size change in it shifts `luaV_execute` and all later code: the textbook confound. | `sieve`, `array_stream`, `tbl_array`, `spectral` (stores into existing array cells) |
| [`abf8b1cd`](https://github.com/lua/lua/commit/abf8b1cd4a798fada026b4046e9dbc08791963f2) "Small optimization in 'luaH_psetshortstr'" (2024-12-28; 5.5 development) | Also fast-paths the creation of new short-string keys in new tables ("constructors like {x=e1,y=e2}"); no measurement. +63/−18 lines in `ltable.c`. | A larger rewrite of a hot table path, again before `lvm.o` in link order. | `methods` (`setmetatable({x=…, y=…})` per call), `tbl_hash` (new short keys), `nbody` (body constructors) |
| Jump tables, `LUA_USE_JUMPTABLE` (5.4.0-work2, 2018; [`893f382e`](https://github.com/lua/lua/commit/893f382e94e05578063f91830ee735f48ee95c8b), [`c72ac048`](https://github.com/lua/lua/commit/c72ac048b989bea0f66f8532ab00a598da71e46d)) | Computed-goto dispatch on by default with GCC/Clang. It is also exactly the dispatch structure whose fetch phase matters here. Testable as a per-arm flag (`-DLUA_USE_JUMPTABLE=0` in `placemat-cflags`) without any history. | every interpreter-bound case |

Also considered, not shortlisted: `4846f7e3` "Micro optimization in OP_RETURN and OP_TAILCALL" (2019, 5.4-beta: too early for this host's 5.4 API to be certain), `2f4162bc` "Compiler optimization back to '-O2'" (only the makefile; this adapter uses its own flags), and `b4b616bd` / `9329eeac` (rehash and resize internals: rare paths in these cases).

## Setup

**Machine.** Apple M2 (4 performance + 4 efficiency cores), macOS (Darwin 25.6), Apple clang 17, ld64. Shared with other timing work: every placemat batch timed under the machine-wide exclusive lock (`amber/pbt/quiet.py --exclusive`, which also waits for the 1-minute load average to fall below 3), builds under its shared lock.

**Lua.** Release tarballs 5.4.6, 5.4.7 and 5.4.8 from lua.org, unpacked in `placemat-work/lua/` (not in this repository). sha256: 5.4.6 `7d5ea1b9…3ad88`, 5.4.7 `9fbf5e28…cfbf1e30`, 5.4.8 `4f18ddae…629ae`. 5.4.6 → 5.4.7 touches 29 files in `src/` (+362/−254 lines: `ldebug.c`, `lvm.c`, `ltable.c`, `lcode.c`, `lstring.c`, the `TString` layout in `lobject.h`, …), which makes it a realistic "adjacent release" change rather than a known speed-up.

**Adapter** (this directory, MIT, no Lua source):
- `build.py` implements the build protocol. Lua's makefile builds `liblua.a` and links `lua.o` against it; here the same sources with the makefile's flags (`-std=gnu99 -O2 -Wall -Wextra -DLUA_COMPAT_5_3 -DLUA_USE_MACOSX`) are compiled directly and linked as objects: `[pad] CORE_O LIB_O luabench.o [placemat_alloc.o]`. The pad is the first code in `__text`; the host and (hooked builds) placemat's allocator come after Lua, so adding them does not move Lua's code. Lua's objects are cached per arm and flags; a variant compiles the pad and host and relinks (about 1 s). After linking it verifies that `placemat_pad` precedes every `lua*` function and that the next function starts at least the pad's size after it (e.g. pad 100 B → `lua_checkstack` at +104: the pad function's `ret` adds 4 B; functions are 4-byte aligned, so every 4-byte pad step moves Lua's code).
- `luabench.c`, a host using only the Lua C API: one fresh `lua_State` per case, a full collection, a discarded `run(1)` warm-up, then the timed `run(n)`; prints `name µs n us` and a checksum comment line; honours `PLACEMAT_CASES` and `PLACEMAT_SERIES` (series = true; no case is fast enough per iteration to be timed as a series, so it is unused in practice).
- `bench/*.lua`: 18 cases written for this survey, 30-130 ms each on a quiet machine (1.2 s per execution): `fib` (recursive calls), `loop_int` (integer and bitwise arithmetic), `loop_float` (Mandelbrot), `str_concat`, `str_format`, `str_pattern` (gsub/gmatch/find), `tbl_array` (append, `table.insert`/`remove`), `tbl_sort` (default and comparator), `tbl_hash` (string keys, `pairs`), `closures`, `methods` (metatables, `__index` chains), `json` (a small encoder), `coroutines` (generators, resume/yield), `array_stream` (three 1 MB float arrays streamed together), `nbody`, `spectral`, `sieve` (an 8 MB boolean array), `vararg` (`select`, `table.pack`/`unpack`).

**Data method: the hook, through `lua_newstate`.** Lua has a pluggable allocator (`lua_Alloc`), so placemat's colouring allocator can be installed from outside without patching Lua: hooked builds (compiled with `$PLACEMAT_CFLAGS`, i.e. `-DPLACEMAT_HOOK`) create every state with `lua_newstate(placemat_lua_alloc, NULL)` (the adapter in `placemat_alloc.h`), stock builds with `luaL_newstate()` (Lua's own `realloc`/`free` allocator). Chosen over the interposer (DESIGN §7) because it colours exactly the interpreter's heap (table arrays and hash parts, strings, stacks), not the C library's own allocations; it needs no `DYLD_INSERT_LIBRARIES` (so it works the same on Linux, and SIP/hardened-runtime rules never matter); and it uses the API Lua documents for this purpose. Either way the wrapper over-allocates large blocks by a header plus colour_span + step_span at every data setting, (0, off) included, so (0, off) is not the stock placement and Lua's GC accounting is unaffected (Lua counts the sizes it asked for). Hence `stock_placement = false`: the stock builds' own result is attributed to "the stock build", code and placement undistinguished (§5.7). The run covariate is `khash` (the k values in allocation order), since `placemat_alloc` reports no region and its base (the first large block's address) is fresh in every run. Unit 64 B (Lua needs 16-byte alignment, `LUAI_MAXALIGN`), colour span 16 KB (the page), step span 16 KB (M2's L1D set stride), coloured blocks ≥ 64 KB (arrays of 4096+ values, big strings and buffers). Linking `placemat_alloc.o` after Lua means a hooked pad build has the same Lua code layout relative to the pad as an unhooked one, but `__text` starts 232 B later in hooked builds (larger load commands), so all of Lua moves by that much between the stock build and pad builds as well.

**Design.** placemat's defaults for a survey (DESIGN §5.7): data axis both (colour and hashed step), three settings per pad, 7 rounds per batch after a discarded execution of each binary and setting, 4 pads then 2 at a time while the 95% half-width exceeds 1%, cap 12; the stock builds timed as one more slot in the first batch; run seed 0.

## placemat issues found

Core bugs:
1. **Crash at the first anchor whenever there is a data axis** (fixed; the only core change). `runner.py`, `Runner.run`'s `slot_env` passed the anchor slot id `a1` to `Design.parse`, which expects `<pad>.<kind>`: `ValueError: not enough values to unpack (expected 2, got 1)` at `design.py` `parse`, `j, k = vid.split(".")`. With `--data none` `slot_env` returns before parsing, which is why `--data none` runs never hit it. Every adaptive run with colour or step that reaches a second batch crashed. Fix (one line): `j, kind = (0, STOCK) if slot.startswith("a") else D.parse(slot)`. An anchor is pad 0 at the stock setting, so it gets exactly `0.s`'s environment.
2. **A crash loses the whole run.** The raw file is written only at the end, so the crash above threw away batch 0's timings (about 5 minutes of timing, after about 45 minutes of lock waits), the failure mode ISSUES P002 lesson 5 warns about. Writing the raw file after every batch, and resuming from it, would bound the loss.

Design and statistics gaps:
3. **The code test has little power under heavy-tailed noise** (above): a rank-based within-round statistic found effects at p ≤ 0.01 that the trimmed-mean statistic put at 0.03-0.47. Worth evaluating as the code test, or alongside it.
4. **Adaptive stopping on the change interval stops a null run at the first batch,** where the code test has 4 pads. A survey's null run should time a fixed, generous number of pads (16 here), or stop on the code test's precision too.
5. **`culprits` could not see threaded-dispatch interpreters** (partly addressed since: it now reports the address phase separating slow from fast pads), and without `--hot` it offers cold-function loops as candidates. Suggest a phase check (slow and fast pads separated by hot-function address mod 8/16/32/64), and requiring or encouraging a hot list.
6. **Data flags under a wrapper whose (0, off) is not stock.** The report should set the stock slot against each data setting, so that "the stock build runs like the offset settings, only the wrapper's (0, off) is slow" (`tbl_array`) is visible and not read as a Lua data problem.
7. **Disturbances inside a batch go undetected.** The noise probe runs only at a batch's start and end, and quiet.py checks the load only when it takes the lock. A per-round check (each round's median ratio to the batch median across all slots) would mark disturbed rounds; they could be dropped or down-weighted for the spread tests, which are not paired.
8. **Reporting.** The "waiting for the machine lock" figure counts only the exclusive lock; the shared-lock wait for builds (252-2380 s here) is reported as build time.

9. **The stock-build pair's interval is overconfident.** In the gated null run both stock builds are one binary, yet 4 of 18 cases came out *measurable* (+4.7%, −5.7%, +3.7%, −3.0%, intervals excluding 1), producing *placement* verdicts "attributed to the stock build". The percentile bootstrap over 7 per-round ratios ignores run-to-run (ASLR, machine) variation between executions; a null-calibrated threshold, or a bootstrap over more stock executions, would be needed before calling a stock difference measurable.
10. **The noise probe measures spread, not level.** A whole batch ran about 35% slower (load 4-5, probably slower cores or a lower clock) while the probe's spread was 1.2-3.3%, so the gate let it through. Paired results survive, but absolute times, the stock pair and between-batch comparisons do not; the probe could also compare its median with a stored quiet-machine reference.

Gaps another agent fixed during this work: the build cache key now covers the adapter's own files (it covered only the arm's tree and `[build]`, so a changed `build.py` or host reused stale binaries), and `placemat culprits` now exists (it first failed to import).

## Linux arm64 (Lima VM)

Build checks only. A timing run in the VM would have held the shared lock for 20+ minutes while six surveys queued for the exclusive one, and VM timings are less trustworthy anyway.

- Lima VM `placemat` (Ubuntu, aarch64, 4 vCPUs, gcc 15.2, Python 3.14), sources through the shared mount. `build.py` builds the stock, padded and hooked variants unchanged (`-DLUA_USE_LINUX`, `-ldl`). The pad check passes: no Lua function precedes `placemat_pad`. Checksums match the Mac's, and stock matches hooked. `placemat_alloc` colours on glibc (35 large blocks for `fib` and `tbl_array`, 0 wrapped).
- **gcc aligns functions to 16 bytes at -O2 on aarch64:** a 100 B pad (104 with its `ret`) moves Lua's first function by 128 B. On Linux/gcc the design's 4-byte pad phases collapse to 16-byte steps, and the mod-8 phase effect seen on the Mac (clang, 4-byte function alignment) cannot occur at function granularity. Whether gcc's alignment avoids the effect or just freezes one phase is a question for a Linux run. A placemat config for the VM would use the same `[machine]` lock (inside the VM it is a VM-local lock: `/tmp` is not shared), wrapped from the Mac side in `quiet.py --shared`.
